| 项 | 实测 |

## 1. 硬上限（先算清楚再优化）

每 token 必须从 HBM/PCIe 取得的数据（实测自 `lingxi-bench bytes`，总 payload 234.22 GiB）：

| 类别 | bf16 体积 | 说明 |
|---|---|---|
| 48 层 dense（gdn 3.89 + gr 1.19 + qsa_attention 1.11 + moe_shared 0.44 + moe_router 0.12 + qsa_indexer 0.04） | 6.79 GiB | 每 token 全读 |
| `output_head` | 1.18 GiB | 每 token 全读 |
| **dense 小计** | **7.97 GiB/token** | |
| routed 专家（Q4G64，480 个/token × 2.611 MB） | **1.25 GB/token** | 命中走 HBM、未命中走 PCIe |

- dense 全 BF16 ⇒ 7.97 GiB / 900 GB/s = **9.0 ms** ⇒ **单流上限 ≈ 111 tok/s**（且这还没算 MoE）。
- **结论 1：不把 dense 量化到 W4，200 tok/s 在物理上不可能。** W4 后 dense ≈ 2.1 GiB/token
  + 专家 1.25 GB ⇒ 3.4 GiB ⇒ 理论 ~264 tok/s。

## 3. 现在的结论模型（2026-10-15 第二次修正，覆盖前一版）

一版曾以为"CPU 入队是瓶颈"。**被以下实测推翻**，修正后的模型是：

1. **同步本身极便宜**：空闲 GPU 下 `cuStreamSynchronize` = **1.0~2.4 µs/次**（`LINGXI_SYNCTEST=400/2000`），
   48 次/token 只有 ~0.1 ms。所以"每层 1 ms 的同步"不是同步开销，而是**真的在等 GPU**。
2. **大 kernel 是高效的**：引擎内 `qkvz` GEMV（84 MB）实测 **0.079~0.096 ms**（`LINGXI_KT=1`），
   折合约 900 GB/s~1 TB/s，与微基准一致。所以瓶颈不在主投影。
3. **头（lm_head）**：1.27 GB 的 cuBLAS M=1 + 496 KB logits D2H ≈ **3 ms/token**（`[head]` 探针）。
   D2H 之所以 3 ms，是因为它 stream-ordered 地等前面的 GEMM 完成。
4. **每层 CPU 入队 ≈ 0.23 ms**（`LINGXI_PROF` 的 `[step]`：attn_gr 0.025 + attn 0.106 + moe ~0.1）。
   约 30 个 kernel/层 × 7.2 µs。
5. **每层 GPU ≈ 0.67~0.9 ms**（`LINGXI_KT2` 括号中位数 1.57 ms 含 eprintln 污染，min 0.707 ms；
   无 PROF 时整 token 45 ms / 48 层 = 0.94 ms/层）。

⇒ **模型：每层是"CPU 入队(0.23 ms) → 同步 → GPU 执行(0.24 ms 带宽、实测 ~0.9 ms)"的串行链。**
带宽账（~0.24 ms/层）与实测 GPU 时间（~0.9 ms/层）差 **3.5~4×**，说明 GPU 的内存流水在
kernel 之间反复被喂不饱而掉效——即**CPU 喂数速度与 GPU 执行被每层一次的同步切成一段段**。
这解释了为什么本轮所有"减少 CPU 开销"的改动（scratch 池、GEMV 尾融合、零拷贝路由、
关 event tracking、改同步调度策略）**全部测不出变化**：它们减的是被 GPU 掩盖的那一段。

**被证伪/无效的假设（本轮新增）**：

| 假设 | 实验 | 结果 |
|---|---|---|
| 1 KB 的 router D2H 本身要 ~0.8 ms | 零拷贝映射 host 内存（`MappedHost`，kernel 直接写 host） | 路径确认生效（无 `[d2h]` 行），**速度不变** ⇒ 之前"sync 1.2→0.4 ms"是等 GPU，不是等拷贝 |
| 每层 alloc/free 风暴 | scratch 池 | 无变化 |
| 逐元素 op 单独成 kernel | GEMV 尾融合（GR 8→5、MoE shared 6→4） | 无变化 |
| cudarc 每次 alloc 建 2 个 event | `LINGXI_DISABLE_EVENT_TRACKING=1` | 无变化 |
| `cuStreamSynchronize` 让出 CPU | `LINGXI_SCHED_SPIN=1` | 无变化 |
| 专家槽命中率是主瓶颈 | 命中率 55%→85% | 0.062→0.047 s，几乎不敏感（但 DMA 本身占 ~7 ms/token：`LINGXI_ARENA_NOH2D` 45→38 ms） |
| GPU 被降频 | 采样 `clocks.sm` | 1380 MHz 满频、无节流；但**空转样本是 135 MHz** ⇒ 有大量空隙 |

### 3.1 已修的真实 bug（解锁 CUDA Graph 的前提）

`[ptrprobe]` 显示同一个逻辑缓冲的地址**逐 token 漂移**（+3 块/层），根因是 scratch 池
**take/put 不成对**：`moe.rs` 的 `expert_out`、`out` 与 `layer.rs` 的 `hyper` 是**裸 `alloc`**
却都被 `scratch::put_bf16` 归还 → 池子每层凭空多 3 块，LIFO 轮转被推移。
**修法**：这三处改成从池里取（`scratch::bf16`），并在 PLE 分支把被替换掉的 `hyper`/`ple_out` 一并归还。
修后实测：`层0 mixed_a` 在每个 decode token 都是同一地址 `0x8ec079a00`，`take/put` 计数
每 token 严格相差常数（live=2）。**地址稳定性是 CUDA Graph 能否捕获的先决条件，现已满足。**

### 3.2 六次"有充分依据"的优化全部实测为零（2026-10-15 第三次修正）

这是本轮最重要的结论：**下面每一刀都有微基准/代码依据，但整机 A/B 全部测不出变化**
（`tools/golden/bench.sh` 后段中位数，64~128 token）：

| 优化 | 预期 | 实测 |
|---|---|---|
| scratch 池（消灭每层 30 次 alloc/free） | 0.177 ms/层 = 8.5 ms/token | **0** |
| GEMV 尾融合（GR 8→5、MoE shared 6→4） | 5 ms/token | **0** |
| router 零拷贝映射 host（去掉每层 1 KB D2H） | 最多 38 ms/token | **0** |
| **CUDA Graph（GR 10 kernel → 2 张图）** | 3.3 ms | **0**（0.0480→0.0450，后续复测 0.0460↔0.0460） |
| **CUDA Graph 扩到 MoE 专家段（共 15/30 kernel）** | 5 ms | **0**（0.0450↔0.0470） |
| 高并行度 block GEMV（[320,10240] 26 µs→?） | 3.7 ms | **0，且略慢**（skip-moe 下 0.0270 vs 0.0260） |
| 环境开关缓存 / 关 event tracking / 同步自旋 / 阻塞式 D2H | 小 | **0** |

**唯一测得正的杠杆：专家 H2D DMA** —— `LINGXI_ARENA_NOH2D=1` 把 **0.0500 → 0.0390 s/token（−22%）**。

**唯一稳定的结构分解**（`bench.sh` 中位数，`LINGXI_SKIP` 剥离）：
```
全模型            50 ms/token
GR + attn（去 MoE） 27 ms   ⇒ MoE ≈ 23 ms（其中 DMA ≈ 11 ms）
GR only（去 attn+MoE）11 ms  ⇒ attn ≈ 16 ms
```
且 GR-only 的 11 ms / 48 层 = **0.23 ms/层，而它只有 ~25 MB/层的权重（带宽账 0.03 ms）**
→ **每个 kernel 的 GPU 固定成本 ≈ 23 µs**（10 个 kernel/层）。把微基准里逐 kernel 的时间
加总只有实测层的 ~55%，说明还有一半是**kernel 之间的 GPU 间隙**——而这正是 CUDA Graph
**消不掉**的（图只是把同样的 kernel 背靠背提交，间隙在 GPU 侧）。

⇒ **结论：真正的墙是"每层 ~30 个 kernel × ~15~23 µs 的 GPU 固定开销"。能动的只有一条路：
把 kernel 数从 ~30 压到 ~8（大融合核），预估 15 ms/token（33%）。**
这也是唯一与"六次为零"自洽的解释。

### 3.3 对 200 tok/s 的现实评估

按已实测的系数外推（都以当前 50 ms/token 为基准）：

| 手段 | 系数 | 依据 |
|---|---|---|
| 专家 DMA 归零（提高命中率/加槽/降专家字节） | ÷1.28 | `NOH2D` −22% |
| kernel 融合 30→8 | ÷1.5 | §3.2（估） |
| dense W4（大 GEMV 是带宽受限的，4x 更少字节） | ÷1.3 | §1 + launch-bench（大形状 700 GB/s） |
| MTP 投机 ×2~3 | ÷2.5 | 需自训 draft（**产物里没有 MTP 头**） |
| CPU 喂数 / 同步 / alloc | ÷1.0 | 六次实测为零 |

全部相乘 ≈ 6.2× ⇒ **~8 ms/token ≈ 125 tok/s**。要再翻到 200，需要在以上之外**再**砍一半
（例如把 30 个 kernel 融到 4~5 个、专家也走 W4、或投机接受率更高）。**200 不是单点突破，
而是"融合 + 量化 + 投机"三件事都做到位的结果。**

### 3.4 【重大过程教训】用错 build 校验方式，导致一整批 A/B 结论作废

上一节那些"六次为零"的结论里，**有三次是在构建失败、跑的是旧二进制的状态下测的**。
我的校验是 `cargo build 2>&1 | grep -cE "^error(\[|:)"`，而 `grep -c` 在某些流式输出下
没匹配到编译错误，于是 `ERRCOUNT=0` 骗过了我 —— 二进制 mtime 比源码旧 32 分钟。

**铁律：只认 `cargo build` 的退出码**：
```bash
cargo build --release -p lingxi-bench > /tmp/build.log 2>&1; RC=$?
[ $RC -eq 0 ] || { tail -30 /tmp/build.log; exit 1; }
cp -f /dev/shm/lingxi-target/release/lingxi-bench bin/lingxi-bench
```
重测后更正的结论：
- **block GEMV 其实是小赚**：0.0450 → **0.0430 s/token（−4.4%）**（之前误测成"略慢"）。
- **CUDA Graph 当前是坏的**（`LINGXI_GRAPHS=1` 启动 `cuStreamBeginCapture` 报
  `CUDA_ERROR_INVALID_VALUE`），所以它的收益**至今未被测量**，不能断言为零。
  默认关闭，不影响主线。

### 3.5 本轮真正的交付：**批量专家路径**（prefill 从"越用越崩"变成可用）

**问题**：`rows > 1`（prefill / 投机验证）原来走**逐专家**路径 —— 每层对每个非空专家
（长 prompt 可达几百个）各发 2 次 cuBLAS GEMM，而且 `load_hits` 会按
`s * 2*inter*hidden` 预分配 bf16 解量化 scratch（`s` 是命中专家数，长 prompt 上万）
→ **显存直接爆**：实测 `s≈880`（88 token）时旧路径 OOM 崩溃，
**prompt 长度实际上被卡在 ~100 token**。

**解法**：把"每对 (专家, 行)"当成 decode 快路径的一个独立 GEMV 行：
```
gather_rows(x, rows_dev) → Q4 直读 gemv(gu) → swiglu → Q4 直读 gemv(dn)
                        → moe_combine_rows(按行加权归并)
```
**只要 5 个 kernel / 层，与 token 数无关**。`rows == 1` 时"对列表"与原来的专家列表完全相同，
所以 decode 路径**完全不变**（`a_stride=0` 共用第 0 行）。

三道在 bring-up 中打出来的真 bug：
1. 我把 gu/dn 的预分配改成惰性后，Q4 直读分支仍在返回 `sc.gu.unwrap()` → 需要一个 1 元素
   **stub** 占位（否则 panic；且 stub 绝不能被当成真权重读）。
2. `gemv_q4g64_slots_bf16` 的 `a_stride` 是 x 的**行步长**：rows==1 时对全共用第 0 行（0），
   rows>1 时 x 是 gather 出来的 [S, hidden]，必须传 `hidden`（否则每对都读第 0 行 → 首 token 变 1076）。
3. `want_q4` 必须与"调用方会不会走 Q4 直读"一致，否则调用方会拿 stub 当真权重读 → 非法访问。

**实测**（`bench.sh` 口径，prefill = "prefill 用时" − "层 47/48"）：

| prompt | 旧逐专家路径 | 批量对路径（新） |
|---|---|---|
| 22 token | 0.20~0.30 s | **0.20 s（9.1 ms/slot）** |
| 88 token | **崩溃（OOM）** | **0.30 s（3.4 ms/slot）** |
| 176 token | 崩溃 | **0.70 s（4.0 ms/slot）** |

且 t=5 的 prefill 仍逐位命中 golden `11751`，decode 不变（0.043~0.046 s/token）。

**意义**：单 token-slot 成本从 decode 的 ~46 ms 降到 **~4 ms（11×）**，
而且**长 prompt 不再受显存限制**——这才是 agent/工具调用场景（长 system prompt + 长上下文）
真正的瓶颈。

### 3.6 稠密 W4（本轮第二大交付：实测 −13%，但长序列下不稳定）

**为什么做这个**：`launch-bench` 分形状表显示，所有**大**形状的 bf16 GEMV 都已经在 ~700 GB/s
的带宽墙上（[8192,2560]=725、[2560,8192]=695、[6144,2560]=633 GB/s）——这些是纯带宽受限，
小 kernel 的固定开销/调度都动不了它们，**只有减字节**。于是给最大的几块稠密矩阵做了
W4G64（group 64 + FP16 scale + nibble 二补码，与专家 arena 同一解码契约）。

**实现**（全部在本轮新增）：
- `lingxi-model/src/q4.rs`：bf16 → Q4G64 在线量化（RTN，group 64，按 64 取 amax，码位限 [-7,7]）
  + 设备句柄 `Q4W`（`payload = base 平面 | pad 到 256 | scale 平面`，与 `matrix_layout` 一致）。
- `lingxi_gemv_q4g64_dense_epi`（融合反量化 GEMV，带 `row_off` 以切同一矩阵的行段）
  **与 `lingxi_dequant_q4g64_dense_bf16`**（t>1 时按需还原成 bf16 走 GEMM）。
- 接入：`gdn/query_key_value_z`、`gdn/output`、`attention/query_key_gate_value`、`attention/output`
  （QSA 两块由 `LINGXI_DENSE_Q4_QSA=1` 单独控制）。W4 模式下**不再上传这些矩阵的 bf16**，
  省下的 ~6 GiB 正好留给专家槽。

**关键实测（`launch-bench` 新增的 Q4 vs BF16 同形状对比）**：

| 形状 | bf16 payload / 带宽 | Q4 payload / 带宽 | 净收益 |
|---|---|---|---|
| [16384,2560] (`gdn/query_key_value_z`) | 40 MB（两次）/ 725 GB/s | 21.2 MB / **321 GB/s** | **1.67×** |
| [2560,6144] (`gdn/output` 等) | 30 MB / ~700 GB/s | 8.0 MB / **257 GB/s** | **1.85×** |
| [13312,2560] (`qsa/qkgv`) | 68 MB / ~700 GB/s | 17.3 MB / **311 GB/s** | **~2.2×** |
| [320,10240] (`gr mix_down`) | 6.2 MB / 257 GB/s | 1.7 MB / **66 GB/s** | **更慢**（所以这里不用 W4） |

**尾数 → 整机**：`LINGXI_DENSE_Q4=1` 让 decode 从 **0.0430~0.0460 → 0.0390 s/token
（21.7~23.3 → 25.6 tok/s，−13%）**，两次复测一致；t=5 prefill **仍逐位命中 11751**。

**⚠️ 已解决（2026-10-15 第六轮）**：那个非确定性 `CUDA_ERROR_ILLEGAL_ADDRESS` **不是 Q4 的问题**，
而是**我新加的「瘦长 GEMM」`lingxi_gemm_skinny_bf16_epi` 的越界读**：
它 8 路展开、把 `m` 用不到的累加器也算一遍，于是无条件读 `x[m*k .. 8*k)`。
- 非 W4 时 `x` 是池里的大缓冲 → 越界恰好落在已映射内存上 → **一直没暴露**（但已经是 UB）；
- W4 的 `t>1` 路径给的是**刚好 `n*k` 的**解量化缓冲 → 必崩，`CUDA_LAUNCH_BLOCKING=1` 下 4/4 复现；
- 修法：把用不到的累加器的行指针**夹回第 0 行**（`xrow[r] = x + (r<m?r:0)*k`）。

修后：`LINGXI_DENSE_Q4=1 [LINGXI_DENSE_Q4_QSA=1]` 连续多次 96/150/200 token **全部通过**
且首 token 仍 11751。**所以 QSA 那两块也是同一根因，不需要单独开关。**

### 3.7 A/B 方法论：**必须固定 token 流**（本轮新增的工具）

实测：同一个配置，只换一段 token 流，decode 耗时就能 ±7%（因为 token→专家路由→槽命中率→DMA 全变了）。
这足以把 10% 的真实增益淹没（本轮的 W4 就先被误判成"更慢 20%"，又被误判成"更快 13%"）。
所以新增 `LINGXI_FIXED_IDS="13,561,6511,..."`：decode 时**强制喂固定 token 序列**
（`Sequence::decode_token` 里只覆盖"下一步吃什么"，返回值仍是真实 argmax）。
固定流下的对比（48 token，两次复测）：

| 配置 | s/token |
|---|---|
| 默认（全 BF16） | 0.0470 / 0.0450 |
| `LINGXI_DENSE_Q4=1`（GDN 两块） | 0.0430 / 0.0450 |
| `+LINGXI_DENSE_Q4_QSA=1`（全部四块） | **0.0410 / 0.0420（−10%）** |

**结论：W4 稳定、可复现 −10~13%；建议开启**（代价：载入时多 ~20 s 的主机端量化）。

**⚠️ 仍未解决（原第 2 条）**：最开始"W4 更慢 20%"的假象 —— 当时 bf16 与 Q4 **两份都留在显存**
（+1.4 GB，逼近 32 GB）。改成"只留 Q4 + t>1 按需解量化"后，既修掉回归也拿回了增益。

### 3.8 t=k 前向的真实成本（本轮新增 `LINGXI_FWD_BENCH`）——**决定投机能不能成立**

`LINGXI_FWD_BENCH="1,2,4,8,12"` 在 48 层全部建好之后、用**空状态**跑纯前向，量的是
"一轮验 k 个 token 要花多少钱"（t=1 与 decode 的 `decode_token` 等价）：

| t | 修复前 | 修复后 | 每 token-slot | 相对 t=1 |
|---|---|---|---|---|
| 1 | 32.1 ms | 37.1 ms | 37.1 | 1.00× |
| 2 | 110.1 | 84.2 | 42.1 | 1.14× |
| 4 | 127.3 | 114.2 | 28.5 | 1.30× |
| 8 | 192.3 | 154.5 | 19.3 | **1.92×** |
| 12 | **593.9** | **236.4** | 19.7 | 1.88× |

三处修复：
1. **t≥9 的 cuBLAS 悬崖**（t=12 的 594 ms）：`use_skinny` 原先只覆盖 t≤8，t>8 掉回 cuBLAS
   → 现在**任意 t 都按 8 行切片**循环调瘦长 GEMM。t=12 **−60%**，且成本回到线性。
   （这也是历史 prefill 数字难看的根因。）
2. **瘦长 GEMM 按 m 特化**（m=1..8 各一个内核）：原实现固定开 8 个累加器、每元素发 8 次
   LDG+FFMA → 权重带宽只有 **215 GB/s**（GEMV 是 724）。特化后 **m=1 725、m=2 671 GB/s**；
   m=4/8 仍退化到 400/333（x 的 8 行 load + FMA 把指令发射顶住了）。
3. **逐行 kernel 循环**（`gr_write` ×2、`mix_mean` ×2 原来 `for row in 0..t` 每行发一次）
   → 改成 `blockIdx.y` 一次覆盖所有行。

**战略结论**：t=8 一轮只有 **1.92×** 摊薄（100% 接受率下）。PLD 之类若接受率 ~50%，
净收益 <1×。要把投机变成通往 200 的路，必须让 **m=8 的稠密投影回到 ~700 GB/s**
（现在 333）——那需要真正的**分块 GEMM**（shared-memory 铺 x），而不是现在的 warp-per-row
瘦长核。**只要 t=8 一轮能压到 ~25 ms，投机就能在 40% 接受率下把单流推到 200+。**

### 3.9 把 Q4 GEMV 从 328 → 372 GB/s（本轮，W4 再快 4~5%）

W4 的净收益被 Q4 核自身的效率吃掉了一半：**Q4 GEMV 只有 ~330 GB/s，而 bf16 GEMV 有 724**，
所以"字节省 3.77×"实际只兑现 1.7~2.2×。根因是**指令密度**：每读 0.5 字节权重就要配
1 次 x load + 1 次 FMA + ~3 次 nibble 位运算，天生是 bf16 的 ~3 倍。三处改动：

1. **一个 warp 算 4 行**（`lingxi_gemv_q4g64_dense4_epi`）：x 的 8 个 load + 8 次 bf16→f32
   转换只做一次、被 4 行共用。**实测只对 k≤3072 有利**（[16384,2560] 344→372 GB/s）；
   k=6144 时 4 组 pay/sca 指针 + xv[8] 把寄存器顶爆，反而 268→177 → 所以**按 k 选核**。
2. **per-group scale 提出内层**：8 个元素只做 1 次缩放乘（原来 8 次）。
3. 尾融合/8 列 u32 大端 load 保持（lane 间连续 4 字节 → 完美合并）。

| 形状 | 改前 | 改后 |
|---|---|---|
| [16384,2560]（qkvz） | 328~344 GB/s | **372 GB/s** |
| [2560,6144]（output） | 268 | 265（按 k 走单行核） |
| [13312,2560]（qsa qkgv） | 331 | **351 GB/s** |

整机（固定 token 流，48 token）：默认 **0.0450/0.0460** → W4（旧核）0.0430 → **W4（新核）0.0410/0.0420**。
即 **W4 合计 −9~10%，其中本轮的核优化贡献 4~5%**。

**下一步的天花板**：若 Q4 GEMV 能到 ~700 GB/s（需要更彻底的手段，例如把 nibble 直接
构造成 bf16 用 packed FMA、或换 int8+`dp4a` 的 A8 路线），稠密投影那 ~20 ms/token 会再腰斩
——那才是 W4 该有的 2× 而不是现在的 1.35×。

## 3.10 A/B 方法论必须换口径：**固定 token 流 + p10**（本轮最重要的工具修正）

同一份配置重跑 4 次，**中位数在 0.0390~0.0440 之间摆（±13%）**——足以把 10% 的真实增益
完全淹没。这也解释了 §3.2 里那批"六次优化全为零"的结论为什么不可信。

换口径后（`tools/golden/ab.sh`）：**`LINGXI_FIXED_IDS` 钉死喂给下一步的 token 序列 +
取后 3/4 个 token 耗时的 p10**，同一配置重跑 4 次是 **0.0370 / 0.0380 / 0.0380 / 0.0380**
（±2.6%）。**此后所有 A/B 都用这个口径。**

> p10 而不是中位数：中位数里混着偶发的 DMA 风暴（槽未命中）停顿，p10 反映的是
> "流水顺畅时的稳态"，更适合比内核效率。

## 3.11 PLE 的两处真问题（`plet.rs`）

1. **`ngram_ids` 每 token 把整段历史重算一遍**（`O(L·heads·ngram)`，heads=120、ngram=3）。
   decode 下调用方只要末尾 `t` 行 → 改成只算末尾 t 个位置（数值完全不变）。
   不修的话 host 时间随上下文线性增长（实测 300 token 上下文时该单项就 ~5 ms/token）。
2. **95 GiB 的 PLE 表每 token 要 120 次随机 `pread`**（表在机械盘上，随机读=寻道）。
   新增进程内**行缓存**（`LINGXI_PLE_CACHE_MB`，默认 1024 MB，FIFO 淘汰）。
   同一段对话里 ngram 行会反复命中（相邻 token 的 n-gram 窗口只平移一格），所以一次就够。
   缓存与否**不改变数值**。

## 3.12 CUDA Graph：从"捕获失败"修到"可用且数值正确"（三个真 bug）

`LINGXI_GRAPHS=1` 现在可用，48 token 输出与 baseline **逐位一致**。修掉的三件事：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | `cuStreamBeginCapture` 报 `CUDA_ERROR_INVALID_VALUE` | **捕获期只"录"不"跑"**：`begin_capture` 里调用的 kernel 不会真的执行。首 token 之后立刻发散（token 2 从 561 变 11），随后路由乱跳、DMA 风暴，速度掉到 0.2 s/token | 录完**立刻 `g.launch()` 一次**，把这一遍本该产生的计算补上 |
| 2 | 每 token 出现 **984 次"固定缓冲重新分配"** | `key=0` 撞车：主干末端的 `hyper_connection_mixer` 和 **layer 0** 共用 key 0，同一 `(key,slot)` 在 `dim=10240` 与 `hidden=2560` 之间来回翻 | 新增 `graph::NO_CAPTURE` 保留 key，`gated_residual_forward` 改用它（**再也不用 0 表示"不录图"**） |
| 3 | 图的输入地址漂移 | 残差流 `x` 从 scratch 池借，`put(旧 hyper)/hyper=next` 的轮转让**奇偶层拿到不同缓冲**（实测 layer 47 的 `hyper` 每 token 在 `0x8e6f56a00`/`0x8e6f4ca00` 间摆） | 在**图外面**先把 x 拷进私有暂存块（`take_fixed(key, slot=8)`），图里只认这块固定地址 |

**实测收益**：只录 GR 的 10 个 kernel/层 → 整机 **−4%**（0.0400 → 0.0380，p10 口径两次复测）。
比预期小：说明**CPU 入队并不是主要瓶颈**，瓶颈在 GPU 侧的 kernel 自身与层间同步。

## 3.13 GEMV 内核：**128-bit load 是通用解**（本轮唯一稳定的正收益）

`launch-bench` 新增"三种核并排"的一行（warps-per-row | 一行一 block 标量 | **一行一 block 128-bit**）：

| 形状 | warp/row | block(标量) | **row8(128-bit)** |
|---|---|---|---|
| [ 8192, 2560] | 724 | 323 | **754** |
| [ 2560, 8192] | 695 | 430 | **790** |
| [ 6144, 2560] | 629 | 318 | **729** |
| [  320,10240] | 252 | 377 | **667** |
| [ 1280, 2560] | 551 | 277 | **634** |
| [  512, 2560] | 349 | 250 | **387** |
| [10240,  320] | **585** | 79 | 270 |
| [ 2560,  640] | **493** | 143 | 389 |

**结论**：瓶颈从来不是带宽，而是"每线程只发 2 字节标量 load"的指令/延迟链。一行一 block
+ 一次读 16 字节（8 个 bf16）后，几乎**所有 k ≥ 1024 的形状都变快**；反过来 k 小时
（mix_up 的 k=320、shared_down 的 k=640）每个 block 活太少，启动开销占主导，warps-per-row 更好。
→ `gpu.rs::use_row8(kdim) = kdim ≥ 1024 && kdim % 8 == 0`，`LINGXI_NO_ROW8=1` 回退。

**整机**（p10，192 token）：全 warps-per-row **0.0410 → row8 0.0370（−10%）**，两次复测一致；
首 token 仍 11751、token 序列 `13,561,6511,314,9564,369` 与 golden 完全一致、文本连贯。

## 3.14 本轮被**证伪**的两条路（都做了完整实现 + 实测，值得留档）

**（一）融合 GR：5 kernel → 2 kernel，实测更慢。**
思路是把分组 RMSNorm 折进 `mix_down` 的 GEMV 读通路（借 DeepGEMM `sm90_tf32_hc_prenorm_gemm`
的"reduce 寄生在 A 读上"），一次出 `d`+`injw`，再用第二个 kernel 出 `mixed`（不落 `imw`）。
微基准（`launch-bench` 新增 GR 块总账，秒级、不用加载产物）：

| | µs/块 | GB/s |
|---|---|---|
| 旧 5 kernel | 50.4 | 262 |
| 新 K1（down+inject） | 45.0 | — |
| 新 K1+K2 | 62.8 | 210 |

⇒ 整机 **0.0390 → 0.0430（−11%，两次复测一致）**。
途中定位到一个真 bug（**`S[g]` 用运行期下标 `g` 会被 nvcc 落到 local memory**，改
编译期常量下标后 K1 从 ~90 µs 降到 45 µs），但即使修好，K1 也只是"打了平手"：
它读的字节比旧路径多（x、gamma 各多读 324 遍），而"省下的那个 13 µs 的 block_inject"抵不过它。
**结论：融合不是万能药，必须"融掉的 kernel 的固定开销 > 融合引入的额外流量"才成立。**
代码保留在 `gr_ops.cu` + `LINGXI_GR_FUSE=1`（默认关，便于后续再试）。

**（二）共享内存 x 的稠密 Q4 GEMV：更慢。**
假设"每个 warp 都把 x 重读一遍（k=2560 → 4096 warp × 5 KB = 20 MB，和权重 payload 一样大）"，
于是把 x 一次性搬进 shared（转 f32）。实测**全面变慢**：

| 形状 | 现核 | shared-x |
|---|---|---|
| [16384,2560] | 370 GB/s | 324 |
| [ 2560,6144] | 268 | 125 |
| [13312,2560] | 349 | 284 |
| [ 320,10240] | 66 | 26 |

⇒ **x 的重复读是 L2 命中，不是瓶颈**；added `__syncthreads` + shared load 反而更贵。
Q4 GEMV 真正的限制是**每读 0.5 字节权重就要 ~4 条指令的 nibble 解码**（指令密度）。
（kernel 已删除，只留结论。）

## 3.15 本轮其余三项（两项实测中性，一项 opt-in −3%）

| 改动 | 实测（p10，192 token） | 处置 |
|---|---|---|
| **lm_head 走 W4G64**（`LINGXI_HEAD_Q4=1`）：1.18 GiB bf16 → 0.31 GiB，顺带把 0.87 GiB 显存让给专家槽 | 0.0370/0.0380 → **0.0370/0.0360（−3%）**，首 token 仍 11751、序列一致 | **保留为 opt-in**（不改默认）：输出头量化对长链路执行质量最敏感，交给用户拍板 |
| **MoE top-k 去整段排序**：原来 `vec![0..512]` + `sort_by`（带闭包，`512·log512` 次比较 + 每行 4 KB 分配）→ 改成 `top_k` 趟手写 selection（`top_k·512` 次无闭包比较），等价性证明：稳定排序对相等元素保留下标升序，而手写 selection 取"严格更大"即同义 | 0.0370/0.0370/0.0380 → **中性** | **保留**（去掉了每层 3 次分配与比较器闭包，代价更低、语义等价） |
| 共享内存 x 的 Q4 GEMV | 全面更慢 | **删除**（见 §3.14） |

**这一节的教训**：本轮**五个已落地的改动合计只把 p10 从 ~0.0380 推到 0.0360~0.0370**。
说明这台引擎的时间是**摊在 ~1350 个小 kernel 和 48 个层间往返上的**，
不存在"砍一刀就翻倍"的单点——必须走 §4 里 P0/P1 的结构性动作。

## 3.16 【本轮最大单项】专家槽 Q4 GEMV 之前**从没被单独量过**，实测是 decode 最大的单块内核开销

`launch-bench` 补上了"专家段"这一格（按 arena 契约复刻 blob：gu `[10,1280,2560]` 1,740,800 B
+ down `[10,2560,640]` 870,400 B = **2,611,200 B**，与真 arena 逐字节吻合）：

| 版本 | gu [10,1280,2560] | down [10,2560,640] | 每层 | 48 层 |
|---|---|---|---|---|
| **修复前**（每 lane 每次只取 1 字节 nibble） | 88.3 µs / 197 GB/s | 48.8 µs / 178 GB/s | 137.1 µs | **6.58 ms** |
| 换成"一次 32 位 = 8 个 nibble"（与稠密版同一手法） | 52.5 / 332 | 33.9 / 257 | 86.4 | 4.15 ms |
| x 侧再改一次 16 字节（8 个 bf16） | 46.7 / **373** | 30.8 / **282** | 77.6 | **3.72 ms** |

**根因和 §3.13 完全同源**：原实现是 `for (c = lane; c < k; c += 32)`，每 lane 每次只 **1 字节** load
（两个 lane 共用一个字节）——k=2560 时每 lane 要走 **80 次依赖的 1 字节 load**。
稠密 Q4 GEMV 早就有"每次 8 列"的修复（见该 kernel 注释），**但专家槽版一直漏了**。

整机（p10，192 token）：**0.0370 → 0.0340~0.0360**（约 −8%），首 token 仍 11751、序列一致。

顺带把同样的 x 侧 16 字节 load 加到**稠密 Q4 单行版**（`[2560,6144]` 268→**315 GB/s**、
`[320,10240]` 66→**108 GB/s**）；但**稠密 4 行版不能加**——4 行共享 `xv[8]` 时寄存器已紧张，
加一组向量寄存器就掉占用率（实测 [16384,2560] 372→343）。**同一个优化在不同内核上结论相反，
所以每一处都必须单独量。**

### 3.16.1 顺手否掉的一个假设：加专家槽**没用**

把 `LINGXI_ARENA_SLOTS` 从 7000 加到 9500（命中率会更高）：p10 **0.0380 → 0.0380，完全不动**。
⇒ 说明剩下的 DMA 不是"槽不够"，命中率 93.2% 时那点未命中开销已经被别的部分盖住了。
（另外实测 `nvidia-smi` 采样：decode 稳态 **GPU util 93~94%、SM 1380 MHz 满频**——
**这台引擎现在是 GPU 真忙，不是空转**，所以一切"省 CPU / 省 launch"的手段都只能拿到小头。）

## 3.17 【本轮最大单项 / 算法级 bug】稀疏注意力核是 `O(head_dim²·Tk)`，占整机 44%

`launch-bench` 补上 `attn_masked_bf16` 这一格后，数字荒谬到一眼能看出是事故：

| tk（KV 长度） | 修复前 | 修复后 | 加速 |
|---|---|---|---|
| 192 | **1240 µs** | **48 µs** | **26×** |
| 1024 | 7665 µs | 280 µs | 27× |
| 4096 | 32586 µs | 1305 µs | 25× |

**根因**（`attn_ops.cu` 旧版的第三段）：
```cuda
for (int d = tid; d < head_dim; d += blockDim) {     // 每个输出维度
    for (int j = 0; j < Tk; ++j) {                   // 遍历所有 key
        for (int dd = 0; dd < head_dim; ++dd)        // ← 把 QK 点积**整条重算**
            s += q[dd] * k[j][dd];
        acc += exp(s) * v[j][d];
    }
}
```
也就是 **QK 点积被算了 `head_dim` 遍**：复杂度 `O(head_dim²·Tk)`，而正确量是 `O(head_dim·Tk)`。
head_dim=256 → **256 倍的冗余**。这也正是"上下文一长就掉到 6.5 tok/s"（§0 里那条 300 token 下
0.153 s/token 的记录）的根因——它随 Tk 线性放大，12 个 QSA 层 × 1.24 ms ≈ **15 ms/token**。

**修法**：重写成"**两遍 + 分 tile**"——每个 warp 负责一个 key（lane 沿 head_dim 分片 + warp 内归约），
点积总共只算两遍（第 1 遍求全局 max，第 2 遍出 exp 并顺便做加权和），exp 落 shared；
tile 循环让任意 Tk 都能跑，不受 shared 容量限制。旧核保留为 `head_dim > blockDim` 的兜底。

**整机**（p10，192 token）：**0.0340 → 0.0270（26 → 37 tok/s，−21%）**；
本轮累计 **0.0380 → 0.0270 = +41%**。首 token 仍 11751、序列 `13,561,6511,314,9564,369` 一致、文本连贯。

**教训（比这个 bug 本身更重要）**：这是一台"**每层 ~30 个 kernel、从来没人逐个量过**"的引擎。
`launch-bench` 的形状表让我抓到了专家 GEMV（6.58→3.72 ms），而**补上 `attn_masked` 这一格
直接抓到 15 ms**。以后任何"总时间远超微基准加总"的情况，第一动作必须是**补全逐核测量**，
而不是去猜"launch 开销"或"同步开销"。

## 3.18 稠密 Q4 GEMV 的"2 倍天花板"是怎么试出来的（四条都试了，都没用）

现状：`[16384,2560]` 21.2 MB payload / 59.2 µs = **376 GB/s**，而 bf16 同形状 800 GB/s。
看起来还有 2 倍，但**试过的四条路全部无效**：

| 尝试 | 结果 | 结论 |
|---|---|---|
| x 搬进 shared（省掉每 warp 重读 5 KB x） | 370 → 324 GB/s（[16384,2560]） | **更慢**。x 的重复读本来就是 L2 命中，加 `__syncthreads` + shared load 反而更贵 |
| 4 个独立累加器打散 8 个 nibble 的 FMA 依赖链 | 314 → 317 GB/s | **无收益**（说明不是 ILP/延迟链问题），且改求和顺序 → 回退 |
| 4 行/warp → 8 行/warp（warp 数减半、x 流量减半） | 微基准 343 → 348，**但整机 p10 0.0270 → 0.0285** | **微基准略好、整机更差** → 回退到 4 行 |
| x 侧一次读 16 字节（对单行版） | 单行版 268 → **315**、[320,10240] 66 → **108** | **有效**（已保留）；但对**4 行版**反而 372 → 343（寄存器已满），所以**4 行版没加** |

**现状判断**：Q4 的 payload 只算 376 GB/s，但把 x 的 L2 重读（4096 warp × 5 KB = 20 MB）
与 scale（1.3 MB）算进去，**真实访存是 ~42 MB / 59 µs ≈ 720 GB/s**——已经接近带宽墙。
再往上要靠**降字节**（不是降指令），那属于量化格式的事（`weight-compression-plan.md` 的
0 阶熵编码 / TCQ），不在内核层面。

## 3.19 MoE 的 9 ms 拆开：**5 ms 是"同步到专家核入队"之间的 GPU 空泡**

`LINGXI_PROF` 的 `[moe]` 行（当前代码，8 token 实测）：

```
[moe] 层 47 shared 0.0000s router 0.0013s (gemm 0.0013 D2H 0.0000 topk 0.0000) 专家 0.0001s 合计 0.0014s
```
- `gemm` = 0.2~1.3 ms —— 这**就是 `k.stream.synchronize()` 的等待**（在等 GPU 跑完本层前半段），不是浪费；
- `topk` < 50 µs（host 端 softmax + top-10 + 打包）；
- `专家` = 100 µs（含 5 个专家核 85 µs + `load_hits` + 2 次 H2D）。

**结构**：GPU 跑完 [L 前半段 + router] → CPU 的 sync 返回 → **但此时流里没有排队的工作**，
CPU 还要花 ~65 µs 做 top-k/取槽/上传/入队 5 个核 —— **这 65 µs GPU 纯空转**，×48 = **~3 ms**。

**为什么不能填**：L+1 的前半段依赖 `hyper_{L+1} = hyper_L' + injw_m ⊗ moe_out`，必须等专家算完；
本层内也没有可提前的活。**唯一能压缩的是那 65 µs 的 host 工作本身**（设备端 top-k + 免掉 2 次上传），
但**设备端 softmax 的 `expf` 与 host 端 libm 的 `exp` 不可能逐位一致** —— 会破坏引擎的位级复现前提，
所以**没做**（留档：这是"速度 vs 位级保真"的取舍，需要用户拍板才动）。

## 3.21 t>1（批量 / 投机验证）路径的真实成本 —— **投机现在完全不可行**

`LINGXI_FWD_BENCH` 重测（当前代码，一次前向的墙钟）：

| t | 总耗时 | 每 token-slot | 相对 t=1 |
|---|---|---|---|
| 1 | 27.1 ms | 27.1 | 1.00× |
| 2 | **93.5** | 46.8 | **3.46×** |
| 4 | 128.5 | 32.1 | 4.75× |
| 8 | 157.7 | 19.7 | 5.82× |
| 12 | 219.8 | 18.3 | 8.11× |

**t=2 就要 3.46 倍** —— 不是"权重只读一遍所以接近 1 倍"，而是每一块都变慢：

| 块 | t=1 | t=2 | 倍数 |
|---|---|---|---|
| GR | 3.4 ms | 10.3 ms | 3.0× |
| MoE | 8.9 ms | 33.6 ms | 3.8× |
| attn | 9.1 ms | 38.5 ms | 4.2× |
| 其余 | 4.8 ms | 11.1 ms | 2.3× |

**三个根因**（都在 t>1 专属路径里）：

1. **Q4 稠密投影在 t>1 时"先整块解量化成 bf16 再 GEMM"**（`proj_q4_epi` →
   `dequant_q4g64_dense_bf16`）。以 `qkvz`（21.2 MB Q4）为例：读 21 MB + 写 42 MB bf16 +
   GEMM 再读 42 MB = **105 MB**，而 t=1 只要 21 MB —— **5 倍**。这是 attn 变 4.2× 的主因。
2. **瘦长 GEMM 的 grid 是 `n/8` 个 block**（warps-per-row），而 t=1 的 row8 是 **n 个 block**
   —— n 小的时候（GR 的 mix_down n=320）并行度差 8 倍。这是 GR 变 3× 的主因。
3. **MoE 的"对"路径不做专家去重**：8 个 token × 10 个专家 = 80 个"对"，同一个专家的权重
   被读 8 遍。批量路径的专家流量因此是 t=1 的 ~3.3 倍（应为 ~1.2 倍）。

**投机解码的判据**：一轮验 k 个 token 的收益 = `(α·k + 1) / (C(k+1)/C(1))`。
以 k=8、α=0.8（乐观）算：`(6.4+1)/5.82 = 1.27×` —— 只值 1.27 倍，还要搭上一套草稿机制。
**⇒ 现在做投机是负收益。**

**要让投机变成通往 200 的路，必须把 C(8) 从 5.82× 压到 ~1.5×**，即把上面三条修掉：
- 写一个**直接吃 Q4 的 m≤8 GEMM**（shared 里解量化 + 分块），替掉"解量化成 bf16"的中转；
- 瘦长 GEMM 改成 **row8 式的"一行一个 block + m 个累加器"**，把并行度拉回来；
- MoE 批量路径**按唯一专家分组**（gather 已在，只需把 `blockIdx.y` 从"对"改成"唯一专家"
  并在块内循环它的 m 个 token，权重就只读一遍）。

三条都是"同样的 kernel、同样的数值、只改并行结构"，**不碰位级复现**。做完 C(8) 预期 ~1.5×，
配合 α=0.8 的 PLD（不需要 draft 模型，靠上下文 n-gram 匹配）→ `7.4/1.5 ≈ 4.9×`。

## 3.22 【战略结论】200 tok/s 单流**就是 t=1 的理论极限本身**

把每 token 必须读的权重重新算一遍（当前配置：GR/MoE-shared 是 bf16，其余稠密是 W4，专家是 W4）：

| 每层 | 字节 |
|---|---|
| GR（mix_down 6.55 + mix_up 6.55 + inject 0.08）× 2 块，bf16 | 26.4 MB |
| GDN 稠密（qkvz 21.2 Q4 + output 8 Q4 + a/b 0.5） | 29.7 MB |
| MoE shared（gate_up 6.55 + down 2.8）+ router 0.5 | 9.9 MB |
| 专家（10 × 2.61 MB Q4） | 26.1 MB |
| **合计** | **~92 MB/层 ⇒ ×48 = 4.4 GB/token** |

4.4 GB ÷ 900 GB/s = **4.9 ms/token = 204 tok/s**。

**⇒ 单流 200 不需要投机——它就是"把每个 kernel 都跑到 90% 带宽"这条路的终点。**
现在的 27 ms 与 4.9 ms 差 5.5 倍，拆开是：
- **Q4 那一半流量只跑到 373 GB/s**（41%），bf16 那一半跑到 750~800（83~89%）；
- 每层 ~30 个 kernel 的固定开销 ~2.8 µs × 30 × 48 ≈ **4 ms**；
- MoE 的 host 往返空泡 ≈ **3 ms**；
- 未与 GPU 重叠的 host 工作（head 的 248320 元素 argmax、PLE、分配）≈ **2 ms**。

**所以两条路都能到 200**：
- **A（不投机）**：Q4 内核从 41% → 85% 带宽，再把 kernel 数与空泡各砍一半。
- **B（投机）**：把 C(8) 压到 1.5×，用 PLD 拿 ~4.9×（需要先修 §3.21 的三条）。

### 3.22.1 修正：路径 A **到不了** 200（Q4 是 ALU 受限，不是带宽受限）

上面按"Q4 也能跑到 900 GB/s"算出了 204 tok/s 的上限，**这个假设是错的**。把 Q4 与 bf16
的每字节指令数摆在一起就明白了：

| 格式 | 每 8 个权重需要的指令 | 每字节权重的指令 |
|---|---|---|
| bf16 row8 | 1×int4 W load + 1×int4 x load + 8 cvt + 8 FMA ≈ **18** | 1.1 |
| **Q4（4 行版）** | 1×u32 W load + 8 x load/cvt + 8 FMA + 8×(2 位移/掩码 + 2 比较/取补) ≈ **53** | **13** |

Q4 的负载是 bf16 的 12 倍，而每字节权重少一半 —— **净 6 倍 ALU**。实测 Q4 373 GB/s、
bf16 800 GB/s ≈ 2.1 倍差距，与 ALU 差距的方向一致。
**试过的 4 条降指令密度的路（§3.18）全部无效**，说明 4 位解码在 V100 上已经到头。

换 8 位格式（A8 = int8 + `dp4a`）能把每 4 个权重的指令压到 3 条（**8 倍降**），
但字节翻倍：`[16384,2560]` 41.9 MB ÷ 900 = **47 µs**，而现在是 59 µs —— **只赚 20%**，
却要换整套量化格式 + 给激活也加量化核。**不划算。**

**⇒ t=1 的现实下限**：Q4 那半（1.76 GB @ 373）+ bf16 那半（2.64 GB @ 780）≈ 8.1 ms，
再加每层 30 个 kernel 的固定开销（~4 ms）与 MoE 空泡（~3 ms）⇒ **~15 ms ≈ 67 tok/s**。
**单流 200 靠路径 A 达不到。**

**⇒ 唯一够得着 200 的是路径 B（投机）**，而它的前提是把批量路径从 5.82× 压到 ~1.5×：
t=8 的重量下限其实和 t=1 同量级（权重只读一遍，4.4 GB + 专家去重后的 ~3.7 GB ≈ 8 GB
@ 500 GB/s 混合 ≈ 16 ms），而现在跑 157.7 ms —— **差 7 倍，这 7 倍就是全部机会。**


## 3.23 批量路径第一刀：**瘦长 GEMM 的并行度**（已落地，t=8 −18%）

按 §3.21 的三条根因动手，**第 2 条（瘦长 GEMM 的 grid 只有 `n/8` 个 block）先修**：

新增 `lingxi_gemm_skinny_row_bf16`：**一行一个 block**（grid = n，与 t=1 的 row8 同款并行度）
+ 128 位 load + m 个独立累加器，尾融合语义与旧模板完全一致。
`gpu.rs::use_skinny_row(kdim) = kdim ≥ 1024 && kdim % 8 == 0` 分派（判据与 `use_row8` 同源）。

| t | 修前 | 修后 | 变化 |
|---|---|---|---|
| 1 | 27.1 ms | 28.0 ms | ±0（t=1 不走这条路） |
| 2 | 93.5 | 89.9 | −4% |
| 4 | 128.5 | **103.4** | **−20%** |
| 8 | 157.7 | **128.8** | **−18%** |
| 12 | 219.8 | **159.6** | **−27%** |

`C(8)/C(1)` 从 **5.82×** 降到 **4.60×**。投机的判据 `(α·8+1)/(C(8)/C(1))` 在 α=0.8 时
从 1.27× 升到 **1.61×** —— 方向对了，还差得远（需要 ~1.5×）。

**同时证伪一条**：MoE 的"唯一专家分组"（`lingxi_gemv_q4g64_slotsm_bf16`，已实现并接线，
`blockIdx.y` = 唯一专家、块内循环它的 m 个 token）——**实测 t=8 157.7 → 158.9，没有收益**。
原因是这一趟的 8 个 token 路由**重叠本来就少**（S=80 个对，唯一专家数并没有明显下降）。
代码保留（对"同一专家被多 token 命中"的场景是对的），默认走新核。

**剩下两条**（按收益排序）：
1. **Q4 稠密在 t>1 时"先解量化成 bf16 再 GEMM"**（§3.21 根因 1）——这一条最大，但要写一个
   **真正的分块 GEMM**：W 的 Q4 块解量化进 shared + x 也进 shared（否则 x 会被每个 block 重读，
   n=16384 时是 655 MB 的 L2 流量）。≈200 行 CUDA + 调参。
2. 小 t（2~4）时干脆**按 token 循环 t=1 的 row8 路径**：流量 `t × 21 MB` 对 t=2 是 42 MB，
   而现在是 105 MB —— **小 t 反而更快**（大 t 不成立）。

## 3.24 批量路径第二刀：**分块 Q4 瘦长 GEMM**（已落地，t=8 −23%）

修 §3.21 根因 1（"t>1 先解量化成 bf16 再 GEMM"）。新增 `lingxi_gemm_q4_skinny_bf16`：
`grid = ceil(n/8)`（8 个 warp，**warp-per-row**）、k 按 1024 分块、每块把 `x[m][1024]` 协同搬进 shared、
每个 lane 一次吃 8 列（1 个 u32 = 8 个 nibble）——**解码一次被 m 个 token 复用**。

| t | 本轮开始 | +瘦长 GEMM 并行度 | **+分块 Q4 GEMM** |
|---|---|---|---|
| 1 | 27.1 | 28.0 | 26.9（不走这条路） |
| 2 | 93.5 | 89.9 | **62.6（−30%）** |
| 4 | 128.5 | 103.4 | **76.0（−26%）** |
| 8 | 157.7 | 128.8 | **99.6（−23%）** |
| 12 | 219.8 | 159.6 | **128.0（−20%）** |

`C(8)/C(1)`：**5.82× → 4.60× → 3.70×**；投机判据（α=0.8）**1.27× → 1.61× → 2.00×**。
首 token 仍 11751 ✓。

**调试过程（三个真 bug，都靠新加的 `launch-bench` 自检抓出来）**：
1. `Q4G_ROWS=16` 但 blockDim=256 只有 **8 个 warp** → 每块后 8 行没算（首 token 变 13307）；
2. `bf16 tmp[8]` 中转时 `reinterpret_cast<int4*>(tmp)` 是**未对齐的 128 位访问** → 改成 global→shared 直拷；
3. **漏了 warp 内归约**：每个 lane 只算 32/1024 列，32 个 lane 却都往同一个 `y[s*n+row]` 写，
   谁最后写谁生效 → "所有输出都错、量级只有正确值的 1/10"。

**方法**：`LINGXI_Q4G_TEST=1` 在 `launch-bench` 里自建一个 [512,1024] 随机矩阵，把
**解量化+瘦长 GEMM（GPU）**、**CPU f64 点积**、**新核**三者摆一起比；再用 `LINGXI_Q4G_DBG=1`
切到"一线程一行、逐字节解码"的对照核 —— 对照核正确 ⇒ 问题在优化过的内层循环；
对照核也错 ⇒ 问题在参数/指针。**这一步把定位时间从小时级压到分钟级。**

## 3.25 slotsm 的 21 ms 拆开：**去重收益几乎全在设备侧；nibble 提升被证伪**

`launch-bench` 新增 slotsm 三形状微基准（同一次运行、blob 复刻真权重布局）：

| 形状 | gu | dn | 每层 | ×48 |
|---|---|---|---|---|
| A 真 t=8（e_uniq=80, m=1） | 419 µs | 303 µs | 722 µs | **34.6 ms** |
| B fixed（e_uniq=10, m=8） | 216 µs | 139 µs | 355 µs | **17.0 ms** |
| C t=1（e_uniq=10, m=1） | 58 µs | 42 µs | 100 µs | 4.8 ms |

**结论 1**：`FIXED_EXPERTS`@t=8 省下的 20.9 ms 里 **A−B = 17.6 ms 是设备去重**（权重少读 8×），
host 侧只剩 ~3.3 ms —— 与 SKIP 矩阵 MoE@t8≈59 ms 相容（34.6 核 + gather/swiglu/combine/host）。

**结论 2（证伪）**：B 的权重流量与 C 相同却慢 3.6×，第一嫌疑是"nibble 反量化在 m 循环里
重复 m 次"。把 code 提升出 s 循环（每 word 只解一次，改动数学逐位等价）后 **B 纹丝不动
（216.4→216.4 µs）** ⇒ 不是 ALU 瓶颈。真正的解释在 **grid 几何**：
slotsm grid = (⌈n/8⌉, e_uniq)，B 只有 10×⌈n/8⌉ 个 block，而 gu 段 3200 行 ⇒
**3200×10÷8=4000 block** 但 dn 段只有 320×10=3200 block；每 block 内 8 warp 各扛一行、
k 循环每步 1 次 u32 权重 + m 次 int4 x —— m=8 时 **x 侧 L2 流量 = 权重 ×8**，
C 的"每 block 只干 m=1 行活"反而把 x 流量省了。B 的 80 GB/s 就是 x 重读把 L2/LSU 打满。
⇒ **要救 m 循环得把 x 块搬进 shared（每 block 一次协同装载 m×行段），不是省几条指令的事**。
改动本身无害（m=1 路径逐位等价）故保留。

**结论 3**：C（slotsm m=1）比 slots 核同形状慢 26%（58 vs 46 µs）—— group_off 间接 +
定长 acc[8] 的固有开销；t=1 走 slots 核所以不受影响。

**同场 t=1 SKIP 矩阵**：total 27.0｜−moe 16.6（**MoE=10.4**）｜−gr 23.0（4.0）｜−attn 17.8（9.2）｜
−ple 27.1（0）。MoE 10.4 ms 里设备 gemv 只占 4.2 ms（2×44 µs/层×48 实测 C 形状 ≈ 88 µs/层），
**非-gemv ≈ 6.2 ms = 129 µs/层**：host 空泡 65 µs（§3.19，动它要牺牲位级保真）+ shared/路由/swiglu/
combine 等小核。

**同场 t=2 / t=4 SKIP 矩阵**（同会话）：
t=2 total 63.5｜−moe 28.5（**MoE=35.0**）｜−gr 57.7（5.8）｜−attn 53.6（9.9）；
t=4 total 76.2｜−moe 33.3（**MoE=42.9**）｜−gr 65.8（10.4）｜−attn 65.8（10.4）。
**关键矛盾**：slotsm 微基准按比例预测 t=2（e_uniq≈20, m≈2）应 ≪ A 形状的 34.6 ms，
实测 MoE@t2=35.0 ms 已达 MoE@t8(~59) 的一半以上，且 MoE@t2−MoE@t1=24.6 ms ≫ gemv 增量。
⇒ **t>1 时 MoE 的大头不在 gemv 核内**——嫌疑是 pair_path rows>1 时 graph 外的
`upload_i32/upload_f32`（moe.rs L380-381、L412）+ gather + 每层 sync 空泡。下一刀拆这个。

**t=2 稳态层计时（LINGXI_PROF+FWD_BENCH 实锤）**：稳态每层 `[moe]` CPU 侧 total
t=2 ≈0.9 ms / t=4 ≈1.2 ms（其中 router_stage 0.6/1.0 ms = **router D2H 的 sync 把前面
整层 GPU 活全排空**，×48 层 ≈ 43 ms ≈ SKIP 口径 MoE@t2 全部）。⇒ **[moe] 段本身 CPU 不空转，
t=2 是 GPU-bound**；之前"host 序列化"假设不成立。

**微基准扩形状（同场 launch-bench）**：
D t=2 无重叠（e_uniq=20,m=1）gu 109.7/dn 78.6 ⇒ 188 µs/层 = **.**0 ms；
E t=2 全重叠（e_uniq=10,m=2）⇒ 126 µs = 6.0 ms；F t=4（e_uniq=28,m=2）⇒ 327 µs = 15.7 ms。
**m=2 相对 2×m=1 只慢 ~30%** ⇒ slotsm 的 m 循环本身不吃亏，x 重读解释也弱化了。

**FIXED_EXPERTS@t=2/t=4 同场**：t=2 none 74.0｜fixed **59.8**｜skip-moe 28.5；
t=4 none 77.1｜fixed 66.4｜skip-moe 31.4。⇒ 路由钉住为 t=2 省 **14.2 ms**、t=4 省 **10.7 ms**
（掉槽 DMA + e_uniq 膨胀），远超 t=1 的 ~2 ms —— **t>1 路由每多一个唯一专家就是整份 blob 的
H2D**，投机路径应优先保证专家槽常驻。
钉住后 MoE@t2 = 31.3 ms，设备 gemv（E/D 形状）只占 6~9 ms，剩余与 `[moe]` sync 口径一致：
GPU 时间线上 MoE 段（shared+router+专家+gather/swiglu/combine）实打实 ~0.65 ms/层，
**下一刀回到核吞吐本身：dn 段只有 209 GB/s（gu 301）**。

**端到端复核**：改后 t=1 26.9 ms、t=8 100.6 ms（方差内）；首 token 11751、
序列 `13,561,6511,314,9564,369` ✓；单流 p10 0.0280（run 间方差，slotsm 不在 t=1 路径上）。

**运维坑（本轮实锤）**：`./bin/lingxi-bench` 是**手动拷贝的构建产物**，
`cargo build` 后必须 `cp /dev/shm/lingxi-target/release/lingxi-bench $MODELS/lingxi/bin/lingxi-bench`，
否则跑的是旧二进制（本轮曾因此差点误判）。源码树两侧同一 inode，无需同步。

## 3.26 本轮四件事：多行/warp 证伪、"14.5 µs 地板"被推翻、**首个干净的端到端分解**、两个 CUDA 陷阱

### A. 每 warp 多行（RPW>1）—— **证伪，单调变差**

动机：dn（n=2560, k=640）一 warp 一行时全局 warp 数 25600、每线程只搬 ~10 B，怀疑"线程数过载"。
做法：`lingxi_gemv_q4g64_slots_body<RPW>` 模板 + 每档一个独立核，grid-stride 第 r 轮覆盖连续行集合。

| 形状 | RPW=1 | 2 | 4 | 8 |
|---|---|---|---|---|
| gu 16.6 MB | **47.9 µs** | 53.0 | 63.7 | 67.7 |
| dn 8.3 MB | **31.6 µs** | 33.9 | 39.8 | 43.4 |

**每个档位都更差**。原因：行循环体内含 shfl 归约（warp 级同步），多行是**串行**的、没有跨行 ILP
重叠，反而让可用并行 warp 数下降。⇒「线程数过载」假设不成立（RPW=1 就是最优）。
核保留为对照（`gemv_q4g64_slots_rows_bf16`，默认从未接线到主路径）。

### B. 「~14.5 µs 每 launch 固定地板」是**用 k 做变量拟合出的假象** —— 真 launch 固定成本只有 3.6 µs

新增「微型 launch 探针」（同一 Q4 核，改 S/n/k）：

| 形状 | 耗时 |
|---|---|
| S=1, n=8, k=640（1 block、1 warp） | **3.6 µs** |
| S=10, n=8, k=640（10 block） | **3.6 µs** |
| S=1, n=2560, k=640（1.6 MB） | **5.4 µs** |
| S=10, n=2560, k=640（8.3 MB，真实形状） | **31.4 µs** |

⇒ **launch 固定成本仅 3.6 µs，与 S/n 无关**；31.4 µs 是**吞吐**问题不是地板。
之前 k=128 测出的 14.9 µs 截距，混合了「短循环 fill/drain 低效」与「固定成本」，误判成"地板占 dn 的 47%"。

**真实归因（ALU 定量核算）**：Q4 每字节权重需 ~24 条 FP32 指令（nibble 提取 + 符号扩展 + I2F + FMUL + FFMA）。
- V100 算力 = 80 SM × 64 FP32/cycle = **5120 op/cycle**
- 跑满 900 GB/s 需 600 B/cycle × 24 op/B = **14400 op/cycle** ⇒ **超 2.8 倍**
- ⇒ **ALU 上限 ≈ 320 GB/s**，实测 dn 278 / gu 365 与之一致（与 §3.22.1 同一结论，此处给出闭式核算）

### C. 两个能**吃掉 25%** 的 CUDA 陷阱（后续所有核改造必须避开）

1. **RPW 做成运行时函数参数** → 外层循环无法被编译器消除 → dn **31.6 → 41.6 µs（−25%）**、gu 46 → 56 µs。
   （对照 slotsm 同形状 41.6 µs 完全一致，排除时钟因素。）
2. **多档 RPW 塞进同一个核用 `switch` 分派** → 寄存器/占用率按**最大档**分配 →
   即便走 RPW=1 分支也要 **41.5 µs**（vs 独立核 31.6 µs，**−24%**）。
   ⇒ 正确做法：**模板 + 每个档位一个独立 `extern "C"` 符号**（本轮已改成 `_r2/_r4/_r8`）。

> 位保真：模板化后 RPW=1 展开与历史逐行核**逐位等价**，实测首 token **11751** ✓、
> 序列 `13,561,6511,314,9564,369` ✓。

### D. **首个干净的端到端分解**（`LINGXI_SKIP` 只有在**路由被钉死**时才可信）

⚠️ §3.13 的警告是对的：跳块 → 输出乱码 → 路由乱跳 → 专家槽全失效 → 被剥的块反而更慢。
所以**每一行都叠加 `LINGXI_ARENA_FIXED_EXPERTS=1`**（路由钉死、槽 100% 命中，
kernel 数/launch 数/缓冲/同步点与正常路径完全一致，只是数学作废）+ `LINGXI_FIXED_IDS`
（固定 token 流）。工具：`tools/golden/diag_probe.sh`（N=16，取后 8 个的 min）。

| 配置 | min (s/token) | 推论 |
|---|---|---|
| 基线（固定 ids） | 0.037 | — |
| **固定专家（槽 100% 命中）** | **0.026** | **专家槽 H2D/槽管理 = 11 ms** |
| 固定专家 + `LINGXI_ROUTER_NOSYNC=1` | 0.026 | ⚠️ **无效行**：该开关在当前代码里**已不存在**（只剩本文档/注释引用），此行实际 == 上一行 |
| 固定专家 + `SKIP=ple,moe` | 0.016 | **MoE 块 = 10 ms** |
| 固定专家 + `SKIP=ple,attn` | 0.017 | **attention = 9 ms** |
| 固定专家 + `SKIP=ple,gr` | 0.022 | **GR（超连接）= 4 ms** |
| 固定专家 + `SKIP=ple,moe,gr,attn` | 0.004 | PLE + 其它 = 4 ms |

**11 + 10 + 9 + 4 + 4 = 38 ≈ 37 ⇒ 分解自洽。**

**这张图推翻了本轮开始时的直觉排序**：
- **专家槽 H2D = 11 ms（30%）是单流第一大头**，比任何核内优化的空间都大（专家 GEMV 裸测总共只 3.8 ms）；
- MoE 计算块 10 ms 里，专家 GEMV 只占 3.8 ms，其余 ~6 ms 是 router/shared/combine/空泡（§3.19）；
- attention 9 ms；GR 只有 4 ms（上一轮 skip 测出的"GR=12 ms"是被路由污染的数字）。

**⇒ 下一步优先级：槽 H2D（11 ms） > MoE 块的非 GEMV 部分（6 ms） > attention（9 ms，但归约结构受限）。**
"提前布局权重"的正确含义不是重排核内布局（已证伪），而是**减少未命中槽的 H2D 与槽管理开销**。

### E. 槽 miss 的代价 = **~65 µs/次 host 编排，不是 PCIe 带宽**

`bash tools/golden/run_full.sh "The capital of France is" 32`（`LINGXI_ARENA_STATS=1`）：

```
arena: 48 层 x 512 专家 | blob 2611200 B | 设备槽 7000 (17.0 GiB) | arena_pinned=1
[arena] 命中率 53.0%  (3111/5866)   驻留 2755/7000 槽     ← token 8
[arena] 命中率 66.4%  (7080/10666)  驻留 3586/7000 槽     ← token 18
[arena] 命中率 72.1%  (11144/15466) 驻留 4322/7000 槽     ← token 28
```

- 命中率**随 token 数爬升**（热专家逐渐驻留），稳态 ~70%+；**驻留只用到 4322/7000 槽**（槽还没被填满，
  说明 miss 不是因为"槽位不足"，而是**工作集(48×512=24576 个专家实例)本身就大于 7000**）。
- 算账：每 token 480 个专家实例（48 层 × top-10），命中率 ~70% ⇒ **~145 次 miss/token**。
  11 ms ÷ (48 × ~3.5 miss/层) ≈ **65 µs / 次 miss** —— 与 §3.19 记录的"每层 65 µs host 工作"完全对上。
- **反证带宽论**：145 × 2.6 MB = 377 MB/token，若真是 PCIe 传输主导，x8（~6.5 GB/s 实测）需要 **58 ms**，
  远超实测 11 ms ⇒ **11 ms 是"每次 miss 的 host 编排 + 同步停顿"，不是传输量**。
- 与 `LINGXI_ROUTER_NOSYNC=1` 无收益（0.026 ↔ 0.026）一致：router 的 sync 不是独立瓶颈，
  真正的空泡在**槽 miss 的取槽/上传/入队/DMA 等待**这一段。

**⇒ 三个候选方向（按预期收益排序）**：
1. **降低每次 miss 的 host 编排成本**（批量提交多次 DMA、异步化、避免逐次同步）——直接打 11 ms；
2. **提高命中率**（替换策略按频次而非 LRU；或**用路由预测/MTP 草稿提前预取**专家的 DMA，与计算重叠）；
3. 设备端 top-k / 设备端槽管理（收益最大但**会破坏位级复现**，需用户拍板——见 §3.19 留档）。

### F. ⚠️ 修正：上面那 11 ms 是**冷启动成本**，长序列稳态只剩 ~1 ms

用现成开关 `LINGXI_ARENA_NOH2D=1`（**只记槽不真拷 DMA**，LRU/命中统计/槽号完全不变，数学作废）
做 A/B —— 它直接量出「DMA 传输 + 未重叠等待」的净代价：

| 序列长度 | 命中率 | 正常 | `NOH2D=1` | 差 |
|---|---|---|---|---|
| N=16 | ~60% | 0.036 | 0.026 | **11 ms** |
| N=200 | 93% | 0.027 | 0.026 | **1 ms** |

`run_full.sh` 的命中率爬升曲线（token 8→198）：**53.0% → 66.4% → 72.1% → … → 93.1%**，
驻留 2755 → 6741/7000 槽（仍在上限内爬）。⇒ **槽 miss 是"冷启动期"的问题，槽一旦填满就基本消失**。
`11 ms ÷ 145 miss ≈ 65 µs/次` 也印证：那不是 PCIe 带宽，而是**每次 miss 的 DMA 编排 + 等待**，
且它只在前十几个 token 暴露。

**⇒ 结论修正：长序列稳态（0.027）的真实大块是 MoE 块（10 ms）+ attention（9 ms），槽 H2D 不在其中。**
短 prompt / 对话开头仍会吃到这 11 ms，属于"首次响应"成本（可用预热槽缓解）。

**⇒ 副产物：发现一个比 MoE 更值的独立问题（PLE 表在机械盘上）。**
decode 单 token 耗时呈**双峰**（0.035 ↔ 0.15 s/token，约每 10 个 token 一次尖峰），
`min` 口径把它掩盖了（真实平均约 0.046 s/token 而非 0.035）。
来源已定位：**`$MODELS/qwen4_exp-artifact/qwen4_exp.ple-table.bin` = 95.4 GiB，落在 `机械盘`（机械盘，ROTA=1）**
（`findmnt` 实证），而 PLE 每 token 要按 ngram 哈希**随机取行** ⇒ 页缓存失效时就是一次寻道。
同机 **`sdc`/`sdd` 是 111.8 GB SSD（ROTA=0）**，**容量装得下这 95.4 GiB** —— 搬过去即可消掉这个尖峰（见 §3.27）。

## 3.27 【新发现】PLE 表落在机械盘 ⇒ decode 双峰抖动，**真实平均比 min 差 30%**

### 现象

`run_full.sh`（真实 token 流，未固定）的逐 token 耗时是**双峰**的：
`0.035 s/token` 与 `0.15 s/token` 交替出现，**约每 10 个 token 一次尖峰**。
`min` / `p10` 口径把这个尖峰整个掩盖掉了 —— 稳态真实**平均约 0.046 s/token**，
比文档里到处引用的 `0.027`（p10）差 **~30%**。之前所有"看 p10"的结论都**低估了实际延迟**。

### 归因（已定位到文件与设备）

- `findmnt -T $MODELS/qwen4_exp-artifact/qwen4_exp.ple-table.bin` → **`机械盘`（`ROTA=1`，机械盘）**
- 该表 **95.4 GiB**（`102400491520` B），PLE 每个 token 要按 **ngram 哈希随机取行**（仅 layer 1）
- ⇒ token 流一变，哈希命中新行 → 页缓存 miss → **一次机械寻道**，就是那 ~100 ms 的尖峰

### 验证（决定性）

| 配置 | 逐 token 耗时 |
|---|---|
| `LINGXI_ARENA_FIXED_EXPERTS=1`（token 流被 `LINGXI_FIXED_IDS` 钉死） | **0.026~0.029 稳定，无尖峰** |
| 同上 + `LINGXI_SKIP=ple` | 0.026 稳定 |

钉死 token 流 ⇒ ngram 哈希固定 ⇒ 取的行固定 ⇒ **页缓存全命中 ⇒ 尖峰消失**。
⇒ 尖峰与 PLE 表的**随机读缺页**因果成立，不是别的周期任务。

### 建议（**需用户拍板**，涉及 95 GiB 数据搬迁）

把 `qwen4_exp.ple-table.bin`（95.4 GiB）**迁到 SSD**：本机 `sdc`/`sdd` 均为 **111.8 GB、`ROTA=0`**，
**单块容量就装得下**。预期收益：消掉每 10 token 一次的 ~100 ms 尖峰，
稳态平均从 ~0.046 回到 ~0.027（**≈ −40% 平均延迟**）——比本轮任何核内优化都大。

> ⚠️ 搬迁必须遵守项目铁律：**对 sdb 的连续读写单块 ≤15 分钟、切块 + 歇息**，
> 且**用户逐条确认后才动**（本文件只给方案，不动数据）。
> 若走"表整体放 RAM"路线，注意 95.4 GiB 对容器内存预算的压力（测试容器的 memcg）。

**补充实验（同轮，结论要打折）**：把 host 行缓存从 1 GB 加到 16 GB（`LINGXI_PLE_CACHE_MB`）：

| 缓存 | mean | min | max |
|---|---|---|---|
| 1024 MB（默认） | 0.0348 | 0.0280 | 0.0590 |
| 16384 MB | 0.0329 | 0.0270 | 0.0550 |

**只改善 ~5%**，而且本轮**没能复现那个 0.15 尖峰**（max 仅 0.059）。
原因：系统**页缓存（buff/cache 145 GB）其实已基本装下 95.4 GiB 的表**，
⇒ "随机读缺页"只在**冷页缓存/首次读**时暴露；一旦表被 page cache 兜住，PLE 就不是瓶颈。
**所以 §3.27 的结论要打折**：机械盘确实是隐患（首次读、页缓存被挤时），但**稳态下页缓存已覆盖**；
`LINGXI_PLE_CACHE_MB` 加大收益有限（page cache 已是第二层缓存）。
**待专项确认**：那个"每 10 token 一次 0.15 s"尖峰的**精确触发条件**（本轮第二次实测未复现，
疑似与 cold page cache 或 arena 的 pin 分块有关，需在清空 page cache 的条件下重测）。

### 方法论修正（本轮附带，影响所有历史结论）

**`p10` / `min` 口径会掩盖尖峰。** 本轮所有"0.027 s/token"都是 p10，
而同一配置的 **mean 约 0.033~0.035**；遇到冷页缓存时可到 0.046+。
⇒ 今后 A/B 必须**同时报 mean 与 max**（`bench.sh`/`ab.sh` 目前只报 min/p10，需补）。

## 3.28 【代码调研】MoE 块那 6 ms 的三个靶子（并纠正两条过时结论）

对 `moe.rs` / `arena_source.rs` / `graph.rs` / `qsa.rs` / `gdn.rs` 做了一次逐行调研，三条**改变判断**的结论：

### ① ⚠️ 当前默认 decode 路径的 MoE 专家段**根本不在 CUDA Graph 里**（推翻 §3.20 的旧结论）

`moe.rs:349-352` 选中 `pair_path` 分支（arena Q4 直读），它在 `moe.rs:376-434` 里**直接裸 launch**：
`gemv_q4g64_slots_bf16`(gu) → `swiglu_bf16` → `gemv_q4g64_slots_bf16`(dn) → `moe_combine_rows_bf16`，
外加 `upload_i32(pair_rows)` / `upload_f32(pair_wts)` 两次锁页 H2D（`moe.rs:380-381`）。
**整层共 ~11 个 kernel + 2 次 memcpy，没有一个进图。**
只有 `moe.rs:483-487` 那个 `graph::run_cached(k, layer*8+7, ...)` 分支（bf16 紧凑路径）才录图 ——
而 arena 直读时 `q4_hits.is_some()` ⇒ `pair_path=true` ⇒ **永远进不去**。
（`LINGXI_NO_PAIR_MOE=1` 可以强制回到会被录图的分支，这是验证"录图到底值多少钱"的现成杠杆。）
真正的图覆盖只有 **GR 块**：`gr.rs:88` `capture = graph::enabled() && gkey != NO_CAPTURE && rows==1`。

### ② shared expert 走 **bf16**，`LINGXI_DENSE_Q4` **不覆盖它**

`moe.rs:125-133`：`shared_gate_up [1280,2560]`（6.55 MB bf16）+ `shared_down [2560,640]`（3.28 MB）+
`router [512,2560]`（2.62 MB）+ `shared_expert_gate [1,2560]`，
**全部是 `gemv_bf16*`**（`moe_ops.cu`），合计 **~12.45 MB/层 ⇒ 598 MB/token**。
`main.rs:2728-2735` 的 Q4 分支**不含 shared 权重** ⇒ 稠密 W4 那一刀**没砍到 MoE 里的这块**。
按 §3.22 的 bf16 ~780 GB/s 估 ≈ 0.77 ms + 3 个 elementwise + 4 次 launch ≈ **~1 ms/48 层**。

### ③ host 侧每层有 **512 个 `Vec` 堆分配**（`moe.rs:211` `vec![Vec::new(); num_experts]`）

×48 层 = **24576 次堆分配/token**；再加 `moe.rs:290-327` / `380` / `437-446` 约 8 组打包 `Vec`。
它们全部落在 `moe.rs:181` 那次**全流 `synchronize()` 返回之后、专家核入队之前**的窗口里 ——
也就是 §3.19 说的那段"GPU 纯空转 65 µs/层"。**同步栅栏 + 这段 host 工作 = MoE 块里除 GEMV 外最大的一块。**

### 下一轮的三个靶子（按性价比）

1. **把 MoE 专家段也纳入 CUDA Graph**（或至少把 2 次 H2D + 4 次 launch 收进一次图重放）——
   现在每层 11 个裸 launch × 48 = 528 次入队，是 §3.19 空泡的直接来源。**风险**：pair_path 的
   `slot_ids`/`pair_rows`/`pair_wts` 每层变，录图需先把它们改成"固定缓冲 + 就地写"。
2. **消除/缩小 `moe.rs:181` 的全流同步窗口**：把 host 路由工作（512 Vec 分配、softmax/top-k）
   提前或在另一个线程做，或把 softmax/top-k 下沉到设备端（**后者会破坏位级复现，需用户拍板**）。
3. **shared expert 转 Q4**（把 `LINGXI_DENSE_Q4` 扩到 shared）：598 MB → ~150 MB/token，
   但 Q4 是 ALU 限（~320 GB/s vs bf16 ~780 GB/s）⇒ 实测才算数，预计小赚或不亏。

**其他可用开关复核**：`LINGXI_KT2=1`（单层 GPU+CPU 独占时间，`layer.rs:225-238`）、
`LINGXI_KT=1`（GDN 单核 GPU 时间）、`LINGXI_NO_PAIR_MOE=1`、`LINGXI_GR_FUSE=1`（默认关）。
**注意**：**没有任何开关能把 attention 的 QSA(12 层) 与 GDN(36 层) 分开计时**（`SKIP=attn` 是两类一起跳）。

### 3.29.1 为什么 200 tok/s 恰好是 HBM 的物理地板（算术）

每 token 必须从 HBM 搬的字节（Q4 已按 0.5 B/参数计入）：

| 项 | 字节/token |
|---|---|
| MoE 专家（10 × 2.6 MB × 48 层） | **1.25 GB** |
| attention 投影（GDN: qkv_z 21 MB + o 7.9 MB，×36；QSA: fused 17 MB + o，×12） | **~1.25 GB** |
| **lm_head（仍是 bf16：248320 × 2560 × 2）** | **1.27 GB** ← 单块最大 |
| MoE shared + router（bf16，§3.28②） | **0.60 GB** |
| GDN 递推状态（读+写 3.1 MB × 2 × 36 层） | **0.23 GB** |
| 合计 | **≈ 4.6 GB** |

- 900 GB/s ⇒ **5.1 ms/token = 196 tok/s 就是地板**（要求 **100%** 带宽效率）

- 而 §3.16.1 实测 **GPU util 93~94%、SM 满频** ⇒ **不是空转**，是访存/指令效率
  （Q4 解码核实测 350~376 GB/s，§3.18 已穷尽共享内存/多累加器/多行/shared 四条路）

**⇒ 200 tok/s 等价于要求 5.3× 的访存效率提升；V100 上单流自回归做不到。**

MTP 权重已在产物里（`n_mtp: 1`、`mtp/fc_embedding|fc_hidden|embedding_norm|hidden_norm`、`mtp/layers/0/*`），
但 `lingxi-driver/src/lib.rs:7` 明确写着"**当前实现：单序列贪心（batch=1，无采样/MTP/前缀共享）**"——**尚未实现**。

1. **`rows>1` 时完全没有 CUDA Graph** —— `gr.rs:88` `capture = ... && rows == 1`，
   且 `gr.rs:83-87` 给 rows>1 换了个 `gkey` 段但仍不捕获；MoE 的 `pair_path` 同样裸 launch。

- (a) 把 router 的**零拷贝映射路径扩到 `rows>1`**（去掉每层那次 D2H+sync）——最小改动、可单独验证；
- (b) 给 `rows>1` 的 GR 段做**按 t 分键**的图捕获（`gkey` 再叠 `rows` 维度），把 ~10 次裸 launch 收成 1 次。

## 3.32 【重大更正】Q4 解码不是带宽受限，是**发射率受限** —— nibble→float 查表把 MoE 专家核拉回 +20~26%

### 证据：直接看 SASS（`cuobjdump -sass`，`$MODELS/cuda-12.4/bin/`）

`lingxi_gemv_q4g64_slots_bf16` 热循环里，**每解码一个 4-bit 权重（半字节）要 7 条指令**：

```
SHF.R.U32.HI  R18, RZ, 0x4, R23     ← 移位取出
LOP3.LUT      R18, R18, 0xf         ← 掩码
ISETP.GT.U32  P1, PT, R18, 0x7      ← 判是否负数   ┐ 纯解码开销
@P1 LOP3.LUT  R18, R18, 0xfffffff0  ← 条件符号扩展  ┘
I2F           R31, R18              ← int→float
PRMT          R32, RZ, 0x7610, R8   ← bf16→f32
FFMA          R30, R30, R33, RZ     ← 只有这一条在算
```

（`slots_bf16` REG:40，**occupancy 不是瓶颈**。）

### 定量：为什么吃不满带宽

| | 值 |
|---|---|
| 满带宽需要 | 900 GB/s ÷ 80 SM ÷ 1.38 GHz = **8.15 bytes/cycle/SM** |
| V100 发射能力 | 每 sub-partition **只有 16 条 FP32 通道** ⇒ 一条 32 线程 warp 指令占 **2 cycle** ⇒ 4 个 sub-partition 合计 **2 warp-instr/cycle/SM** |
| 一条 warp 指令的产出 | 32 lane × 1 列 = **16 字节**权重 |
| 原实现 | 56 条 warp 指令处理 8 列/lane（=128 字节）⇒ **2.29 字节/指令** |
| ⇒ 发射率上限 | 2 × 2.29 = 4.57 bytes/cycle/SM = **505 GB/s**（实测 350~440 ✓ 吻合） |

**⇒ 要满带宽必须做到「≤ 1 条指令 / 2 字节权重」；而解码本身就要 14 条/字节。这就是吃不满带宽的原因。**

### 落地：`__shared__ float2 c_lut[256]`（字节→两个 float）

用**整个字节（含 2 个 nibble）当索引**查 shared 里的表，一次 `LDS.64` 拿回两个 `(float)code`：

```cuda
#pragma unroll
for (int i = 0; i < 4; ++i) {
    const int b8 = (int)((wc >> (8 * i)) & 0xFFu);
    const float2 c2 = c_lut[b8];
    dot = fmaf(c2.x, __bfloat162float(xp[2*i]),   dot);
    dot = fmaf(c2.y, __bfloat162float(xp[2*i+1]), dot);
}
```
- 表 256×8 B = 2 KiB；16 个 float2 落在 16 个 bank ⇒ **同址广播、异址不同 bank，无 bank 冲突**
- **位安全**：表里存的就是 `(float)code`（与 I2F 在 [-8,7] 上逐位相同），累加仍是 `fma(code,x,dot)` 的**同一顺序**、无重结合
- **指令数：56 → 38 条 / 8 列**（SASS 复核），发射率上限 505 → ~744 GB/s

| 核 | 改前 | 改后 |
|---|---|---|
| 专家 gu [10,1280,2560] | 47.9 µs / 347 GB/s | **39.6 µs / 439 GB/s** |
| 专家 dn [10,2560,640] | 31.6 µs / 263 GB/s | **27.6 µs / 315 GB/s** |

**位级判据通过**：首 token **11751** ✓、序列 `13,561,6511,314,9564,369` ✓。
⚠️ **端到端 p10/min 未动**（0.0270 ↔ 0.0270）：专家段只占 3.8 ms / 26.8 ms，2.4% 的改善低于 p10 的 0.001 s 分辨率。

### 未兑现的部分（诚实记录）

- **稠密路径没吃到这份收益**：`dense_epi` / `dense4_epi` 加了同样的 LUT（`dense_epi` 的 REG 从 64 降到 32），
  但 launch-bench `Q4gemv [16384,2560]` **仍是 370 GB/s**（改前 376）⇒ **稠密核不受发射率支配，另有瓶颈**。
  它与专家槽核最大的差别是：**x 被 16384 行重复读**（16384 × 5 KB = **84 MB** 的 L1/L2 流量，是权重 21.2 MB 的 4 倍）。
  稠密投影占 Q4 字节的一半左右，**所以端到端没动**。
- `slotsm`（t>1 批量路径）还没改（它的解码先落到 `code[z]` 数组，改动点不同）。

### 下一步（按证据）

1. **稠密核**：摊薄那 84 MB 的 x 重读（1 warp 算多行 / x 预转 f32 后搬 shared / 预转 f32 减少 8 次 `PRMT`）；
2. 继续压指令：把 x 的 8 次 `PRMT`(bf16→f32) 也摊薄或预转；
3. 给 `slotsm` 也上 LUT。

## 3.33 LUT 的连锁效应：稠密 Q4 的「4 行/warp」**必须翻回单行**（shared 带宽被自己挤爆）

launch-bench A/B（同会话、同数据）：

| 形状 | 4 行/warp（旧默认） | **单行/warp（新默认）** |
|---|---|---|
| [16384, 2560]（GDN qkv_z 族） | 60.4 µs / 369 GB/s | **46.2 µs / 482 GB/s（+31%）** |
| [13312, 2560]（QSA fused 族） | 51.2 µs / 354 GB/s | **35.4 µs / 512 GB/s（+45%）** |
| [2560, 6144]（o_proj，本就单行） | 22.9 / 365 | 22.3 / 374 |

**原因**：nibble→float 表是「**每 0.5 字节权重读 4 字节 shared**」= **8 倍放大**；4 行版每次迭代要做
**16 次 `LDS.64`**（4 行 × 4），整块 SM 的 shared 带宽（128 B/cycle）被自己挤爆。
**⇒ 教训：**"把高频数据放进 L1/shared"**可能反作用**——放进去之后读得太频，shared/L1 自身变成瓶颈。
（单行版 REG 也从 72/64 降到 **32**。）
已把默认翻过来：`LINGXI_Q4_ROW4=1` 可回到 4 行做 A/B。**位级判据 11751 ✓、序列一致 ✓。**

1. **去掉 LUT 的 shared 放大**：用「`SHF.L` 把 nibble 顶到高位 + `SHF.R.S32.HI` 算术右移符号扩展 + `I2F`」
   （3 条纯 ALU，**零 shared 流量**）替代查表——对 4 行版可能反而更好（不再挤 shared）。
2. **x 预转 f32 进 shared**：消掉每迭代 8 次 `PRMT`(bf16→f32)，并去掉稠密核那 84 MB 的 x 重读。
3. **攒批 + L2 驻留**：`slotsm`（t>1）也上 LUT；高频权重用 `cudaStreamSetAttribute` 的

## 3.34 负结果：把 LUT 换成「纯 ALU 符号扩展」**更慢** —— 单行核上 shared 不是瓶颈

线 1（§3.33 的下一步 1）已实测证伪。把 `slots_body` 的解码从「查表」换成零 shared 的
「`SHF.L` 顶到 bit31 + `SHF.R.S32.HI` 算术右移 + `I2F`」：

| 核 | 查表版 | 纯 ALU 版 |
|---|---|---|
| 专家 gu | **439 GB/s** | 420 GB/s |
| 专家 dn | **316 GB/s** | 306 GB/s |

**⇒ 单行核每迭代只有 4 次 `LDS.64`，shared 流量根本不是瓶颈；查表省下的 ~2 条指令/列更值钱。**
（被 shared 挤爆的是**4 行版**——它每迭代要 16 次 `LDS.64`。）
已回退，恢复 gu 438 / dn 307，稠密 [16384,2560] 482 GB/s；位级判据 11751 ✓。

**⇒ 结论：解码方式的选型是「按每迭代 LDS 次数分档」的**——
单行（4 LDS/迭代）用查表；4 行及以上（≥16 LDS/迭代）必须去掉 shared。

## 3.35 【清账 1/2】GDN 层的真账：attention ≈ 235 µs/层，四段全是带宽估算的 2~5.6 倍

新增 `LINGXI_KTS=1`（GDN 分段 GPU 同步括号）。⚠️ **顺带修掉一个真 bug**：旧的 `LINGXI_KT=1` 探针在
`LINGXI_DENSE_Q4=1` 下会 **panic** —— 它引用的是空的 bf16 `query_key_value_z`，`.slice(0..conv_dim*h)`
unwrap 到 None，崩在 `cudarc core.rs:2010`（`gdn_step`）。**所以此前所有 `LINGXI_KT` 测量其实根本没跑起来**，
我两次"没有输出"就是这个原因。已加 `query_key_value_z_q4.is_none()` 守卫。

热态 t=1（N=4，取后 8 条，单位 µs）：

| 段 | 实测 | 纯流量估算 | 倍数 |
|---|---|---|---|
| 投影（qkv_z Q4 + a/b 两个小投影） | **~90** | 43.6 | 2.1× |
| 卷积（`causal_conv1d_silu` + **3×`memcpy_dtod`**） | **~28** | ~5 | **5.6×** |
| 递推（`gdn_recurrent`，174 GB/s） | **~69** | 36 | 1.9× |
| out_proj（Q4） | **~44** | 16.4 | 2.7× |
| **合计** | **~235 µs/层** | ~101 | **2.3×** |

**⇒ 上一轮我按"流量 ÷ 482 GB/s"估 attention = 106 µs/层是错的**：漏算了（a）每层 **6+ 次 kernel 的
launch/ramp/tail**（尤其卷积段那 3 次 memcpy）、（b）a/b 两个 n=48 的小投影、（c）各核在真实路径里的
效率只有微基准的 ~1/2。**结论：attention 里没有"神秘丢失的 10 ms"，它就是"每层 6+ 次 kernel 的真实效率"。**

对账：GDN 侧 36 × 235 µs = **8.5 ms**；QSA 侧（0.611 − 0.154 MoE − 0.062 GR ≈ 0.395 ms/层）× 12 = **4.7 ms**
⇒ 合计 **≈ 13 ms**，与 `SKIP=attn`（FIXED 口径）量到的 ~12 ms **对上**。

**按性价比排序的靶子**：
1. **递推 69 µs @ 174 GB/s**（只有 48 block × 128 线程 = 2.4 warp/SM）——最大的单点低效；
2. **卷积段 28 µs 里 3 次 `memcpy_dtod`**：数据只有几十 KB，**是纯 launch 开销**，可融进 conv 核；
3. 投影 90 µs 里 a/b 两个 n=48 小投影：可合并进同一次 launch。

## 3.36 【清账 2/2】t=2 那 36 ms **不是** MoE 专家核 —— 旧归因被证伪

同一个 `LINGXI_KTS=1` 手法，给 `pair_path` 的专家段插同步括号（`LINGXI_ARENA_FIXED_EXPERTS=1` 消 DMA）：

| | t=1 | t=2 |
|---|---|---|
| 前置（upload/gather） | 132.5 µs/层 | 108.6 µs/层 |
| **专家核 + combine** | **15.0 µs/层** | **13.8 µs/层** |
| **MoE 专家段合计** | **147.6 µs/层 = 7.08 ms** | **122.4 µs/层 = 5.88 ms** |

**⇒ MoE 专家核在 t=2 根本没变慢（还略快）**；`slotsm` 路径是好的。
**⇒ §3.31 里"MoE 块 = 36 ms（t=2）"的归因被推翻**：`SKIP=moe` 省掉的不只是专家核，
还省掉了 **`moe.rs:181` 那次每层全流 `synchronize()`**——去掉这个栅栏会让**整条流水线变深**，
其它所有块也跟着变快，于是 SKIP **严重高估**了自己那一块。**这就是"SKIP 剥块"口径的系统性偏差**
（t=1 时它凑巧接近，因为 MoE 块小、栅栏影响小）。

**⇒ t=2 的 2.85× 悬崖，现在四个候选全被证伪或摊平**：
MoE 专家核**平**（上表）、attention **平**（`SKIP=attn` t=2 只省 11.2 ms ≈ t=1 同值）、
GR ≈ 0、专家核**平**。**⇒ 悬崖在「流水线/栅栏层面」，不在任何单个核里**——
最可能是：`rows>1` 时**全层零 CUDA Graph**（`gr.rs:88` 只在 `rows==1` 捕获）+ router 走
非零拷贝路径（`moe.rs:164` `use_map = rows == 1 && ...`，每层多一次 D2H + `synchronize()`），
**两层栅栏叠加 + 无图重放**，把每层的 ramp/tail 全部暴露出来。

**⇒ 收口结论（两笔账都清了）**：
1. **attention 没有"神秘丢失"**：GDN 实测 235 µs/层（投影 90 / 卷积 28 / 递推 69 / out_proj 44），
   四段是带宽估算的 2~5.6 倍，来自**每层 6+ 次 kernel 的真实 launch/ramp 成本**；
2. **t=2 悬崖不在核里**，在**栅栏 + 缺图**；要修它必须动 `rows>1` 的图捕获与零拷贝路由——
   而按 §3.30.1 的算术，即使修好也只能到 ~68-100 tok/s（单流目标的地板仍是 5.1 ms @100% 带宽）。

## 3.37 靶子 A/B 的执行结果：A 被数值约束锁死，B 只省 3 µs（附"launch 开销"假设的更正）

**靶子 A（`gdn_recurrent` 69 µs/层）——打不动，被数值约束锁死。**
- `#pragma unroll 8 → 16`：**68.2 vs 69 µs，无变化** ⇒ 不是展开深度/MLP 问题。
- 真正的锁：`REG:72` + **只有 48 个 block（80 个 SM 里 32 个全闲）**，而**块结构不能拆**——
  核末尾的 `mean(o²)` 是**跨 dv 的两级归约**（warp 内 `shfl` → `ssum[32]` → warp0 再归约），
  一旦把 `dv=0..127` 拆到多个 block，**归约顺序就变了 ⇒ 破坏位级判据**。
  ⇒ 想提速只能改归约树，那是"换 golden"级别的事，不在本轮范围。

**靶子 B（conv 段 28 µs/层）——已落地融合，但只省 ~3 µs。**
把「hist→cin 拷 / qkv→cin 拷 / conv 算 (kh+t) 行 / 末尾 kh 行→hist 拷」**4 次 launch 融成 1 次**
（新核 `lingxi_causal_conv1d_silu_hist_bf16` + `GdnState.k_hist_next` 双缓冲避开核内写后读竞态；
语义逐位等价：`src = (kh+tt) - (K-1-k)*D`、k 仍升序、silu 同式）。
**实测 卷积 28 → 24~25 µs（只省 3 µs）**，位级判据 11751 ✓。

**⇒ 顺带更正一个我一直用错的假设**：我以为"每层 4 次 launch × 6.6 µs ≈ 28 µs 全是 CPU 开销"，
但删掉 3 次 launch 只省了 3 µs ⇒ **CPU 发射时间本来就藏在 GPU 执行后面**（`synchronize()` 之后
CPU 连发 4 个核，GPU 从第 1 个开始跑，后面几个的发射与执行重叠）。
**所以 §3.35 里"卷积段 28 µs 几乎全是 launch 开销"这句话是错的**——它主要是 GPU 时间
（短核的 launch latency + ramp/drain，一个核最快也要 3~5 µs 墙钟）。

**端到端（同口径 FIXED_IDS，N=200，取后 80）**：

|---|---|---|
| min | 0.0270 | **0.0260** |
| p10 | 0.0280 | **0.0270** |
| med | 0.0290 | **0.0280** |
| mean | 0.0297 | 0.0294 |

⇒ 约 **3.5%**（与 Q4 内核那 +31~45% 的收益量级一致：这些核只占一部分）。

**剩下的靶子 C**（`rows>1` 图捕获 + router 零拷贝扩到 rows>1）**未做**——它只影响 prefill/投机，
对单流目标无益；按 §3.30.1 的算术，修好也只能到 ~68-100 tok/s。

## 3.41 PLE 真账（推翻"PLE 4 ms"）+ 外部依赖审计

### PLE：稳态 0.28 ms，**不是 4 ms**；表**不在页缓存里**，热行才是

新增 `LINGXI_KTS` 的 `[kts-ple]` 分段（layer.rs），t=1 实测：

| | 值 |
|---|---|
| 首次（冷） | **5334 µs** |
| 稳态 | **~280 µs/token**（8 次采样 277~301） |

**⇒ 我此前"PLE ≈ 4 ms"的估计（来自被污染的 `SKIP=ple`）错了 14 倍。**

底层实测（dd / python pread）：
- 顺序读 4 GiB：**215 MB/s**，与 `O_DIRECT` 的 215 MB/s **完全一致** ⇒ **这张 95.4 GiB 的表根本没被页缓存兜住**
  （`buff/cache 150 GB` 是别的数据：mmap 的产物 + arena）。
- 4 KiB 对齐、320 B 随机 pread：**8.65 ms/次**（机械盘寻道）。

**那稳态 280 µs 是怎么来的？** 把行缓存关掉（`LINGXI_PLE_CACHE_MB=0`）**结果一样（275 µs）** ⇒
不是行缓存、而是**页缓存兜住了本 prompt 命中的那十几行**（我那个随机测打在全表冷区，所以 8.65 ms）。

**⇒ 结论**：
1. 稳态没问题（0.28 ms，1%）；`LINGXI_PLE_CACHE_MB` 其实**可以关掉**（页缓存已覆盖同一批热行）；
2. **风险是"换话题/换对话"**：新行未命中时**每行 8.65 ms**——这正是之前观察到的 `0.15 s/token` 尖峰的来源
   （≈17 行未命中）。**这才是 PLE 的真问题，且是延迟毛刺、不是带宽**。
3. **对策**：把表搬到 SSD（`sdc`/`sdd` 是 111.8 GB 的 ZFS 成员，随机读 ~0.1-0.5 ms，比机械盘好 20~80 倍），
   **arena 继续留在内存盘**（它 1.25 GB/token 靠带宽，PLE 只要 5 KB/token 靠延迟——两者诉求相反）。
   搬 95 GiB 需遵守"单块盘连续读写 ≤15 min + 切块歇息"铁律，**且要用户拍板**。

| 每 launch 做的事 | 评估 |
|---|---|
| `bind_to_thread()` → **一次 `cuCtxGetCurrent` 驱动调用** | 真实开销；可缓存跳过，但有跨线程风险 |
| `LaunchArgs { waits: Vec::new(), records: Vec::new(), args: Vec::new() }` | **空 `Vec::new()` 不分配**，免费 |
| `arg()` 逐个 push 进 `args: Vec`（13 个参数 → 1→2→4→8→16，**约 5 次 realloc**） | 真实浪费，可用预分配复用缓冲消掉 |
| `result::launch_kernel` → 直接 `cuLaunchKernel`，无额外分配 | ✓ 干净 |

**实测 `smoke_scale`（裸 launch）：2.69 µs/次（CPU）** —— 比我此前假设的 6.6 µs 好得多。
按 ~1400 launch/token 算 ≈ **3.8 ms CPU/token，但完全藏在 26.6 ms 的 GPU 之后** ⇒ **不是瓶颈**。

**同时也证明"库不背锅"**：我们自己的 **bf16 GEMV 内核实测 724~793 GB/s（80~88% 峰值）**
（`gemv [16384,2560]` row8 = 793、`[13312,2560]` = 787、`[2560,6144]` = 771、`[320,10240]` = 739）。
**时间丢在 Q4 内核（439~514 GB/s vs 它自己的 744 上限）和那 ~19% 的有效带宽上，不在外部库。**

**⇒ 不 vendor `cudarc`**：收益（跳过 ctx 检查 + 预分配 args ≈ 0.5~1 µs/launch ≈ 0.7~1.4 ms/token）
需要改写 ~200 个调用点，性价比不成立。**更划算的等价手段是把更多段录进 CUDA Graph**（一次重放顶掉十几~几十次 launch）。

## 3.42 三个"未解"的裁决：skinny GEMM 是无辜的、t=2 悬崖的真凶是 router 的 D2H、以及 KTS 仪器本身有偏

### 账 3 结案：`m=2` 的 skinny GEMM **没有**只跑到流量的 1/5 —— 那是 KTS 污染出来的假数

用 GR 的**真形状**重做 launch-bench 分档（背靠背、无同步）：

| 形状 | 旧核 `gemm_skinny_bf16` | 新核 `gemm_skinny_row` |
|---|---|---|
| **[320,10240]** m=1 / 2 / 4 / 8 | 219 / 165 / **46** / **37** GB/s | **738 / 608 / 430 / 271** |
| **[10240,320]** m=1 / 2 / 4 / 8 | **628 / 543 / 372 / 262** | 232 / 172 / 113 / 65 |

**两个结论**：
1. `use_skinny_row` 的 **`kdim >= 1024` 门槛是对的**（新核是"一行一 block + k 方向 128 位读"，
   `kdim=320` 时每 block 只读 640 字节，惨败）⇒ **现有分派已最优，没有 bug 可修**。
2. **GR 在 m=2 的 GEMM 只要 10.8 + 12.1 ≈ 23 µs/block**（≈46 µs/层两个 block）。
   此前"200 µs/层、只有流量 1/5"是从 `LINGXI_KTS` 的分段同步读出来的，**被同步成本污染**。

### ⚠️ 方法论修正：`LINGXI_KTS` 的绝对值不可信（只能看相对）

同一配置下 `[step]` 四段之和 × 48 = **33.6 ms**，而 FWD_BENCH 的真值只有 26.6 ms ⇒ **偏高 26%**。
原因：**每插一次同步就把流水线排空一次，段值 = 该段 GPU 时间 + 排空/重填**。
更明显的证据：`mlp_gr` 恒为 100 µs、`moe` 恒为 302~306 µs，**不随 t 变、不随开关图变** —— 那是固定成本，不是工作量。
**⇒ 从本轮起：KTS 只用来定"哪个方向"，绝对值一律以 FWD_BENCH / launch-bench 为准。**

### t=2 悬崖的真凶：**MoE router 在 `rows>1` 时退回 D2H 老路**

判据设计（对"SKIP 剥块"的副作用免疫）：**看"剥掉某块后 Δ(t=2−t=1) 是否塌缩"**，
因为 SKIP 的副作用（少一个栅栏）在 t=1/t=2 上大体一致，做差后被抵消。

| `LINGXI_SKIP` | t=1 | t=2 | **Δ** |
|---|---|---|---|
| 无 | 38.5 | 74.3 | **+35.8 ms** |
| gr | 23.1 | 58.1 | +35.0 |
| ple | 41.7 | 72.1 | +30.4 |
| attn | 33.0 | 63.8 | +30.8 |
| **moe** | 29.2 | 41.6 | **+12.4** ← 塌缩 |

**⇒ 悬崖的 65%（+23.4 ms）在 MoE 块**。再排除：DMA（`NOH2D` Δ=33.1 几乎不变）、
Q4G64 专家核（`NO_Q4GEMM` 更差）、`slotsm` 核本身（launch-bench：m=2 只比 m=1 多 27 µs/层）。
最后在源码里找到：`moe.rs` 的 `use_map = rows == 1 && ...` ——
**`rows==1` 走"GEMM 直写映射锁页内存 + 一次 sync"，`rows>1` 却退回 `memcpy_dtoh` + sync**，
而该处注释自己写着这条老路 **"光这 1 KB 的拷贝就让同步多等 ~0.8 ms/层 ⇒ 48 层 ~38 ms/token"**，
与实测 +35.8 ms 同量级。

**修复**：把映射零拷贝路径放开到所有 rows（`rows>1` 用 `gemm_skinny_row` 直写映射内存，免掉 D2H）。
**位级判据通过**（首 token 11751、序列 `13,561,6511` ✓）。实测：

| 配置 | t=1 | t=2 | Δ |
|---|---|---|---|
| **映射路（新）** | 31.3 | **59.8** | **+28.5** |
| `LINGXI_ROUTER_NODMAP=1`（老 D2H 路） | 26.8 | **73.0** | +46.2 |

**⇒ t=2 前向 73.0 → 59.8 ms（−18%），悬崖 +46.2 → +28.5 ms（−38% = 每层省 275 µs）。**
（t=1 的 31.3 vs 26.8 与本次改动无关——`rows==1` 分支一字未动，两次运行间噪声；
但**这个噪声本身**说明尺子还得修，见下。）

### 顺带纠正：CUDA Graph 的实际收益是 15~19%（不是 11%）

| | t=1 | t=2 |
|---|---|---|
| 图 ON | **27.4** | **60.3** |
| 图 OFF | 33.9 | 71.1 |

⇒ **t=1 省 19%、t=2 省 15%**。（KTS 下算出来的 11% 同样是仪器偏差。）

## 3.43 尺子修好了，并且它一上来就纠正了两个数

### 新 `tools/golden/bench.sh`：完整分布 + 多轮 + 离散度判据

旧版只打一个"后段中位数"。新版每轮报 **min/p10/p50/p90/max/mean/sd**，
并给出**离散度 = (p90−p10)/p50**，**>8% 就标 ⚠️ 不可用于 1~3% 级别的结论**；
跑 R 轮，报「R 轮里最好的 p50」。

### 一上来就抓到的两件事

**(1) "空闲后首跑"会慢 4 倍 —— 这才是 ±5% 噪声的真来源**

同一个脚本连跑三轮（N=200）：

| 轮 | p50 | 离散 |
|---|---|---|
| r1（空闲后首跑） | **0.1480** | 45% |
| r2 | 0.0380 | 39% |
| r3 | 0.0380 | 39% |

⇒ **首跑慢 3.9 倍**（页缓存/CUDA 上下文/锁页缓冲/PLE 冷读全在这时候付），
之后 0.037~0.038 稳定。**⇒ 以后所有测量都必须先跑一轮丢弃的预热。**

**(2) 我之前报的 "p10 0.0270 ⇒ 37 tok/s" 不是真实负载的中位数**

| token 流 | p50 | ⇒ tok/s |
|---|---|---|
| **自然（tokenizer 驱动）** | **0.0370 ~ 0.0380** | **26.3** |
| `LINGXI_FIXED_IDS`（固定 200 token） | 0.0320 ~ 0.0340 | 31.2 |

⇒ **诚实的单流数字是 ~26-27 tok/s**（固定流做 A/B 时 ~31）。此前引用的 0.0270 是"固定流下的 **min**"，
被当成基线用了。**A/B 仍用固定流（保证同一负载），但对外报数必须用自然流。**
（差异来源：固定流的路由是人为选的，专家槽命中率与自然流不同。）

### 轮内离散 31~38% 是**真实的**，不是测量误差

同一轮里 p10→p90 就跨 0.029~0.043。这与前面几次独立发现一致：
**PLE 换行未命中 8.65 ms/行、MoE 专家槽 miss → H2D DMA、路由抖动** —— 都是真实的逐 token 抖动。
**⇒ 单流 decode 的"体验"本来就不是一个常数，而是一个有长尾的分布。**

## 3.44 尺子第二版（µs 精度 + p10 为头条）—— 它当场把一个"零收益"翻成 −5%

### 尺子的最后两个硬伤，都已修

1. **二进制只打 `{dt:>7.3}s/token` ⇒ 1 ms 粒度**。单 token ~33 ms，**量化台阶就是 3%**，
   任何 1~3% 的优化都落在同一个刻度上。已改成 `{:>9.1} µs/token`（0.1 µs 分辨率）。
2. **p50 轮间会漂 5%，而 p10 只漂 2%**。p10 代表"机器干净时"的速度（不受 PLE 冷行、
   专家槽 miss 这些长尾拖累）。`bench.sh` 现在**以 p10 为头条**，p50 作参考。

### 立即见效：`LINGXI_HEAD_Q4` 从"零收益"变成 **−4~5%**

| | p10 | p50 |
|---|---|---|
| 基线 | 29953.9 µs | 33539.1 µs |
| **`LINGXI_HEAD_Q4=1`** | **28735.4（−4.1%）** | **31823.2（−5.1%）** |

（同一配置两轮内部一致：headq4 r1/r2 的 p10 只差 1.1%。）
**⇒ 尺子一修好就还了本：`lm_head` 1.27 GB/token bf16 → W4 0.34 GB，省 ~2 ms。**
⚠️ 它**会改变输出**（lm_head 决定采样），所以 golden 需要重生成 —— 目前保持 opt-in。

**⇒ 连带结论：凡是我以前说"量不出来/在噪声内"的改动，都要用新尺子重测一遍。**
已知名单：`gdn_recurrent` 的 `#pragma unroll`、各次小核合并、`LINGXI_PLE_CACHE_MB`。

### 块账修正（此前 GR/PLE 两项都错了）

| 块 | ms/token | 占比 | 修正说明 |
|---|---|---|---|
| **attention**（GDN 36 + QSA 12） | 13.0 | **49%** | 不变 |
| **MoE** | 7.1 | **27%** | 不变 |
| **GR（两个 block）** | **3.5** | **13%** | ⚠️ 此前写 1%（基于那个错的 6 µs 读数） |
| lm_head | **1.6~2.4** | 9% | bf16；W4 可到 ~0.7 |
| **PLE** | **0.28** | **1%** | ⚠️ 此前写 15%（基于被 SKIP 污染的 4 ms） |
| 合计 | ≈26.3 | 100% | 与 FWD/bench 自洽 |

**GR 为什么是 13%**：`mix_down [320,10240]` + `mix_up [10240,320]` 各 6.55 MB bf16，
每层 2 个 GR block ⇒ **1.26 GB/token = 全量 4.6 GB 的 27%（流量口径）**。
而**它俩是 bf16，没吃到 `LINGXI_DENSE_Q4`** —— 我们量化了 attention 的投影，
却把同样大的 GR 留在了 bf16（**这是个明显的不对称**）。

### 回答"kdim=320 每 block 只读 640 字节"

`gemm_skinny_row` 的设计是**一个 block 包一个输出行 + 沿 k 向量化**。
`[10240,320]` 有 10240 个输出行 ⇒ 10240 个 block，每块的有效载荷只有 `320×2 = 640 B`
（加上读整条 x 行）。**它是给长 k 调的**（kdim≥1024 时每行 ≥2 KB 才摊得平），
短 k 时每块的固定开销压过载荷 ⇒ 掉到 232 GB/s。旧核是 `n/8` 个 block、warps-per-row，短 k 反而对路。
**两条核的适用区间互补，不是 bug，也不需要"提前知道"什么——形状在加载时就全知道了，
而现有分派（`kdim>=1024 ? 新 : 旧`）已经踩在最优的那一侧。**

## 3.45 t=2 前向 74.7 → 45.2 ms：真凶是 cuBLAS 在"极窄 N"上的病态内核

**定位过程（可复现）**：`LINGXI_KTS=1 LINGXI_PROF=1 LINGXI_FWD_BENCH=1,2` 把前向按 48 行一块切开，
得到每段的**真 GPU 时间**（单位 ms/前向）：

| 段 | t=1 正式 | t=2 正式 | Δ |
|---|---|---|---|
| 入口+attn_gr | 7.9 | 8.8 | +0.9 |
| attn | 13.9 | 16.7 | +2.8 |
| mlp_gr | 7.8 | 8.0 | +0.2 |
| **moe** | **14.4** | **43.7** | **+29.3** |

MoE 内部再切三段（`[moe]` 行）：`shared 1.5 → 24.0`（**+22.5**）、`router 3.6 → 4.8`、`专家 9.6 → 14.6`。
GR 反而完美（`[kts-gr] rows=1 71.6 µs` vs `rows=2 68.2 µs` —— m 真的免费）。

**根因**：MoE shared expert 的 `shared_gate_up` 是唯一走 `epi=4`（swiglu 尾融合）的热路径，
而 `proj_t1_epi` 在 `t>1 && epi==4` 时落进"cuBLAS GEMM + swiglu"分支。`gemm_bf16_nt`
把形状摆成 `m=n(1280), n=t(2), k=2560` —— **cuBLAS 面对 `N=2` 这种极窄 N 会选到病态内核**，
单层 50 µs → 500 µs。

**改法**：把该分支的 `gemm_bf16_nt` 换成本仓自研瘦长 GEMM（`skinny_call` → `gemm_skinny_row_bf16`
/ `gemm_skinny_bf16`），同一形状只要 ~10 µs；顺带把 `swiglu` 直接写进 `y`，省掉一块 scratch 与一次 DtoD。
（借鉴源：本仓 §3.21 的"t>1 一律走自研瘦长 GEMM"结论 —— 这次是把最后一处漏网的 cuBLAS 补上。）

**实测（FWD_BENCH，同一台机、同一次会话）**：

| t | 改前 | 改后 | Δ |
|---|---|---|---|
| 1 | 29.8 ms | 28.1 ms | −5.7% |
| 2 | 74.7 | **45.2** | **−39.5%** |
| 4 | 78.9 | **59.5** | −24.6% |
| 8 | 103.6 | **86.7** | −16.3% |

每 token-slot：t=2 37.4→22.6、t=4 19.7→14.9、t=8 13.0→10.8 ms。

**位级判据通过**：首 token 11751 ✓；`LINGXI_FIXED_IDS` 固定流下返回序列
`13,561,6511,314,9564,369,19241,13` 与 golden 逐位一致 ✓（即采样序列仍是自身不动点）。

**顺带解开的账**：本会话开头"1.8 s/token"并非代码回归 —— 那次跑漏了 `LINGXI_EXPERT_ARENA`，
掉进 `MmapExpertSource`（host LRU ↔ device LRU 抖动）回退路。复现：不带该 env 时
prefill 12.0 s / decode **488~714 ms/token**，带 env 时 9.1 s / 55~103 ms。
**这是一条"忘了 env 就静默慢 20 倍"的坑，应删掉或改为硬报错。**

**仍未清的同类**：`qsa.rs::indexer_mask`（indexer 的 q/k 投影）与 `plet.rs` 的 4 处
仍直接用 `gemm_bf16_nt`，t>1 时同样吃到窄-N 病态内核；改动会动 prefill 数值，
需逐处过位级判据后再改。

## 3.46 把外部库（cuBLAS）彻底请出热路径；回退路一律不许静默；尺子加一档

**1) cuBLAS 全部下线**（承接 §3.45 —— 上一轮只修了 `proj_t1_epi` 的 epi=4 一处）。
本轮把**其余所有 `gemm_bf16_nt` 调用点**一并换成自研核：

| 位置 | 原形状（t>1） | 换成 |
|---|---|---|
| `qsa.rs::indexer_mask` 的 q/k 投影 | `[t, q_dim / head_dim, 2560]` | `proj_t1` |
| `plet.rs` 的 key/value 投影（4 处） | `[t, dim / hidden, embed_dim]` | `proj_t1` |
| `trunk.rs` 与 `driver` 的 lm_head | `[t, vocab, 2560]` | `proj_t1` |
| `moe.rs` 逐专家慢路径 | `[m, 2I 或 2560, hidden / inter]` | `proj_t1` |

顺带把 `proj_t1` 泛化成 `W: DevicePtr<bf16>`、删掉重复的 `proj_t1_slice`；
`LINGXI_NO_SKINNY` 整条删除并登记为 Ghost —— 它关掉的正是"自研瘦长核"，
打开就是 `t=2 前向 64.7→405.6 ms`。**至此模型前向里不再有 cuBLAS。**

**2) 回退路一律不许静默**
- `MmapExpertSource`（没给 arena 时的 host LRU 路）：实测 decode **488~714 ms/token**
  （慢 15~20 倍）。现在**直接报错退出**，要用必须显式 `LINGXI_ALLOW_MMAP_FALLBACK=1`
  —— 这正是本会话开头"1.8 s/token"被误判成代码回归的原因（§3.45）。
- `check_env` 新增：**任何 Ab 回退开关一旦被打开就大声警告**，并把实测代价一起打出来。
  历史上多次"忘了关某个回退开关 ⇒ 最优路径被回退了却不知道"。

**3) 尺子第三档：分块计时从"秒 + 4 位小数"改成 µs**
`[step]/[moe]/[gdn]` 原来打 `{:.4}s` ⇒ **台阶 100 µs**，而这些分块本身只有 15~500 µs
（例：MoE 专家段 14.6 µs）—— 台阶比被测物粗 7 倍。改成 µs（0.1 µs 分辨率）。
**为什么不到 ns**：统一用 ns 的判据是"被测物 < 1 µs"，而我们的核没有一个小于 1 µs；
再加三位只是把噪声写得更长。整 token（~30 ms）用 µs、亚毫秒分块用 µs，已经比全部噪声细。

**实测（同一次会话）**：

| t | §3.45 后 | §3.46 后 |
|---|---|---|
| 1 | 28.1 ms | 29.6 |
| 2 | 45.2 | **37.9** |
| 4 | 59.5 | 66.5（轮间方差大，见 §3.44 离散判据） |
| 8 | 86.7 | **81.8** |

每 token-slot：t=2 **18.97 ms**、t=8 **10.23 ms**。

**位级判据通过**：首 token 11751 ✓；固定流序列 `13,561,6511,314,9564,369,19241,13` ✓。
**门限验证**：不带 `LINGXI_EXPERT_ARENA` 直接跑 → 立刻报错退出（不再是静默慢 20 倍）。

## 3.47 尺子修好后重做的块账（固定专家、p10）+ 两个廉价假设被否

`LINGXI_ARENA_FIXED_EXPERTS=1`（钉死路由 ⇒ 槽 100% 命中 ⇒ 去掉冷启动干扰），100 token 取 p10：

| 配置（`LINGXI_SKIP`） | p10 µs | 反推的块 |
|---|---|---|
| 无 | 28,315 | 基线 |
| `ple` | 28,174 | **PLE = 0.14 ms**（稳态几乎免费，§F 再证） |
| `ple,moe` | 17,849 | **MoE = 10.5 ms（37%）** |
| `ple,attn` | 16,745 | **attention = 11.6 ms（41%）** |
| `ple,gr` | 23,565 | **GR = 4.8 ms（17%）** |

0.14 + 10.5 + 11.6 + 4.8 = 27.0 ≈ 28.3（差额是块间交互）⇒ 分解自洽。
**排序更新为 attn 41% > MoE 37% > GR 17%**。

**两个"廉价假设"当场被否（都进 §7）**：
- `LINGXI_SCHED_SPIN=1`（把 `cuStreamSynchronize` 从 AUTO 改自旋）：p10 **27,610 → 27,774**（噪声内）
  ⇒ **同步唤醒延迟不是瓶颈**；
- `LINGXI_NO_GRAPHS=1`：p10 **27,610 → 27,707**（噪声内）⇒ **CUDA Graph 在这台机上一分钱都不值**。

第二条更关键：它说明**系统不是"发射/同步延迟受限"，而是真的"GPU 执行受限"** ——
所以"整层录图消空泡"不值得走，力气应该花在**核内（带宽 + 指令发射）**。

**另纠一处本会话早期的判断**：我一度以为稳态是"PCIe 打满"（miss 流量 ≈ 179 MB/token）。
按 §E/§F 的现成结论核对后不成立 —— 那 11 ms 只在**冷启动期**暴露（N=16 时），N=200 稳态只剩 **1 ms**
（`LINGXI_ARENA_NOH2D` A/B 铁证）。本次 N=64 的 85% 命中里，miss 成本约 3~4 ms，也不构成主项。

## 3.48 数值敏感度的实测标尺：**敏感的是"离散的路由选择"，不是连续的值**

问题背景：A/B/C 三类改动会不会让输出变？先用**同类扰动**标定（`LINGXI_FIXED_IDS` 固定流，8 token）：

| 配置 | 首 token | 贪心序列 |
|---|---|---|
| 基线（稠密全 bf16） | 11751 | `13,561,6511,314,9564,369,19241,13` |
| `LINGXI_DENSE_Q4=1 LINGXI_DENSE_Q4_QSA=1`（**所有稠密投影** → W4G64） | **11751** | **逐位相同** |
| `LINGXI_HEAD_Q4=1`（**输出头** → W4G64，数值最敏感的一处） | **11751** | **逐位相同** |

⇒ **把连续量扰到 W4 级别（相对误差 ~1e-2），词一个都不变。**
反过来，把**专家**从 bf16 换成 Q4（同量级扰动）在自然贪心下却把序列从
`13,561,6511,314` 挪到了 `11,864,369,1048`。

**结论（它决定了 A/B/C 的风险排序）**：这个模型对**连续数值**的扰动极不敏感，
对**离散决策**（512 选 10 的路由）极其敏感 —— 路由一抖，整层走的是别的专家，输出断崖式改变。

- **C（加载时 blocked 重排）**：只改内存布局，值**逐位不变** ⇒ **风险 0**；
- **B（GDN 递推归约顺序）**：只改连续量的求和顺序，量级 ≤ W4 ⇒ **风险很低**（仍需实测确认）；
- **A（设备端 router top-k）**：直接动**离散的路由决策** ⇒ **风险最高**，就是 Q4-专家这一类。

**与"原版官方"的距离怎么量**：本仓已有 HF oracle `tools/golden/run_gen_golden.py`
（用**产物真实权重、bf16**、逐步贪心产 token 序列）—— 那才是官方口径。
但"词变了"≠"质量降了"，后者要 perplexity / 任务精度，token diff 量不出来（见 §7 该条）。

## 3.50 W4 量化产物落盘缓存：启动 **40.1 s → 4.4 s**（比 bf16 基线还快 2.3×）

**原则**（用户定的）：能提前算的全提前算，硬盘/内存里存好，之后**只取**；加载慢无所谓，因为很少反复加载。

**做法**：`LINGXI_Q4_CACHE=<dir>` —— 按**张量名**（不是内容）寻址：

| 时机 | 行为 |
|---|---|
| 首次 | 读 bf16 → 量化 → 落盘 `<dir>/n<hash>.q4` → 上传 |
| 之后 | **直接读那个 1/4 大小的文件** → 上传（**连 bf16 都不读**，也不算哈希） |

**为什么不按内容寻址**：第一版就是按内容寻址（`hash(rows,cols,bits)`），结果**只省掉量化、启动仍 27.6 s**
—— 因为要算哈希就必须先把 6 GiB bf16 读出来。真正的开销是**读**不是算。改成按名字后，
命中路径整段跳过读取 ⇒ 4.4 s。

**实测**（三档 W4 全开，`LINGXI_FIXED_IDS` 固定流）：

| | 启动 | 首 token | 贪心序列 |
|---|---|---|---|
| bf16 基线（无 W4） | 10.0 s | 11751 | `13,561,6511,314,9564,369,19241,13` |
| W4 冷缓存（首次） | 40.1 s | 11751 | 同上 |
| **W4 热缓存** | **4.4 s** | 11751 | **逐位相同** ✓ |

缓存体积 1.7 GB（`/dev/shm`，易失；丢了只是下次重算）。落盘失败**只影响下次还要算**，不影响正确性。

  结构就是 **1 个 MTP 层 + stem**：
  `mtp/fc_embedding[2560,2560]`、`mtp/fc_hidden[2560,2560]`、`mtp/embedding_norm[2560]`、`mtp/hidden_norm[10240]`、
  `mtp/mixer/*`（stem 的 GR）、`mtp/layer/{attn_gr,mlp_gr}/*`（GR）、
  `mtp/layer/attention/{query_key_gate_value,query_norm,key_norm,output,indexer/*}`（**QSA**）、
  `mtp/layer/mlp/{router_shared_gate,routed_gate_up,routed_down,shared_gate_up,shared_down}`（**MoE**）。
- **这些算子引擎里全都有**（qsa / moe / gr）⇒ 这是"移植 + 接线"，不是训练。
- 草稿成本 ≈ 1 个主干层（~0.5 ms），相对 t=2 验证的 37.9 ms 几乎免费。

1. 从 `mtp2` 抽出 27 个 `mtp/*` 张量，追加进生产产物（或做成 sidecar）；

3. **先做离线对拍**：MTP 给的 draft top-1 与主干真实下一 token 的**一致率**（= 接受率）——
   这个数决定投机到底能赚多少，**在动 decode 循环之前必须先拿到**；
4. 一致率够高再进 decode 循环（draft → t=2 验证 → 回卷 KV；回卷机制 M6 已有）。

## 3.52 MTP 移植规格（**权威参考是 llama.cpp，不是 ninfer —— 用户明确说 ninfer 的接受率是错的**）

### 权威来源
`$MODELS/tmp/strata/third_party/llama.cpp/src$MODELS/qwen3next.cpp`
→ `llama_model_qwen3next::graph_mtp`（**第 627–755 行**，以及第 108–120 行的 `load_block_mtp`、第 203 行的输入说明）。

**不要照抄 ninfer**：`$DATA/ninfer-dev/src/targets/qwen4_exp/impl/variant.cpp` 里也有 MTP
（`mtp_attention_projection` / `mtp_kv_projection` / `mtp_q_gate_projection` / `mtp_post_mixer`），
但用户明确告知**它的接受率有问题、大概是错的** ⇒ 只把它当"结构索引"，数值/顺序一律以 llama.cpp 为准。

### llama.cpp 给出的 MTP 草稿头（逐行抄录，别脑补）
1. `h_embd = inp->h` —— 输入是**喂给 lm_head 的那个 post-norm hidden**（第 203 行原文：
   "post-norm hidden state is input to both the LM head and the MTP head"）；
2. `h_norm = RMSNorm(h_embd, hnorm)`；`e_norm = RMSNorm(embed(tok), enorm)`；
3. **`concat = ggml_concat(e_norm, h_norm, dim=0)` ⇒ 顺序是「embedding 在前、hidden 在后」**；
4. `cur = eh_proj @ concat`（`eh_proj` 形状 `[2*n_embd, n_embd]`）；
   **我们的产物把它拆成两个 `[2560,2560]`：`mtp/fc_embedding` + `mtp/fc_hidden`
   ⇒ 等价于 `fc_embedding @ e_norm + fc_hidden @ h_norm`**（顺序由第 3 条钉死）；
5. 然后就是**一个和主干同构的块**（原注释："MTP head is identical to the trunk block
   (full attention + FFN)"）：
   `attn_norm` → `build_qkv(..., n_embd_head*2, ...)`（**Q 里打包了 gate**，对应我们的
   `query_key_gate_value [13312,2560]`）→ `q_norm`/`k_norm` → rope → attention →
   **`cur = attn_out * sigmoid(gate)`** → `wo`（我们的 `attention/output [2560,6144]`）→ 残差 `+ inpSA`；
6. 之后接 FFN（我们的 `mtp/layer/mlp/*` = MoE 512 选 10）；
7. 输出头复用主干的 `text/output_head`（`shared_head_*` 那三个是可选的、我们产物里没有）。

### ★ stem 的**确切换算顺序**（来自 Strata 已验证实现 `src/core/mtp.cpp` L669–693）
（Strata 就是那个跑过 `--mtp mtp/rt --spec 4`、72~87 字符/s 的引擎 ⇒ 这是**已验证**的参考，
不是 ninfer。张量名来自 `strata/mtp/mtp-inventory.md` 的 HF 清单。）

```text
# 分支一：embedding
emb = embed(tok)                                  # [T, N=2560]
en  = RMSNorm(emb, pre_fc_norm_embedding)          # [T, N]（整段 N 宽）
e2  = fc_embedding @ en                            # [T, N]

# 分支二：hidden —— 输入是**残差栈** Rin [T, HC=4, N=2560]，不是 2560 的 hidden！
hn  = RMSNorm(Rin, pre_fc_norm_hidden)             # 逐 stream（每片 N 宽）norm
h2  = fc_hidden @ hn                               # **每个 stream 各投一份** → [T, HC, N]

# 合并：把 e2 **广播加**到 h2 的每一个 stream
R[g] = fc_hidden @ hn[g] + e2        for g = 0..HC-1      # R = [T, HC, N]

# 之后就是**与主干层完全同构**的一段（原注释：MTP head is identical to the trunk block）
R → GR(attn_hyper_connection, 带 block_inject) → xn, mixed
  → QSA attention（q/k/v 打包在 query_key_gate_value[13312,2560]：
     q 里**打包了 gate**，即 q_dim = heads*head_dim 里含 gate 一半；o_proj[2560,6144]）
  → GR(mlp_hyper_connection, 带 block_inject) → MoE（512 选 10）
  → **层尾 `hyper_connection_mixer`（= 主干每层尾部那个不带 block_inject 的 GR）**
  → 复用主干的 text/output_head
```

**两个必须注意的点**（ninfer 出错最可能在这里）：
1. `pre_fc_norm_hidden` 作用在 **10240 的残差栈**上、且是**逐 stream（每 2560 一片）norm**，
   不是对 2560 的 hidden 做 norm；`fc_hidden` 也是**逐 stream 各投一份**（不是只投一份）。
2. 合并是 **`add_streams_broadcast`**：e2 广播到 4 个 stream 后相加 —— 不是 concat、也不是只加一路。

⇒ 引擎里这些零件**全都有**（`gr::gated_residual_forward`、`qsa::attention_forward`、
`moe::sparse_moe_forward`、`trunk::` 的输出头），所以是**接线**；
唯一需要让主干多吐一个东西：**层尾 mixer 之前的那个残差栈**（trunk.rs 里的 `hyper`）。

## 3.53 GR 的账修正：不是"小算子有病"，是"带宽已到墙 + 3 个核的固定开销"

一度怀疑 GR 里 `norm`(16.8 µs) 与 `mix_mean`(13.5 µs) 这两个**几十 KB 载荷的小算子**有病。
查了 `mix_mean` 的 launch：`grid(H/128)=20 blocks × rows`、载荷 40 KB ⇒ **核本身没问题**。
那些数字是 **KTS 仪器自身的排空/重填开销**（§3.42：每插一次同步就排空一次流水），
不是核的 GPU 时间 —— **先查再动手，避开了一次白写的核**。

按 SKIP 口径（可信）反推 GR：**4.0 ms / 48 层 / 2 个实例 = 42 µs/实例**，5 个核：

| 部分 | 载荷 | 时间 |
|---|---|---|
| `mix_down` + `mix_up` | 2 × 6.55 MB | ~18.7 µs（**~700 GB/s，已在带宽墙上**） |
| `norm` / `mix_mean` / `inject` 三个小核 | 20/40/80 KB | ~24 µs（**每个 ~8 µs 的固定开销**） |

⇒ **GR 的 4.0 ms 里：2.2 ms 是已到墙的 GEMV，1.8 ms 是 3 个核的固定开销（×2 实例 ×48 层）。**
要再压只能**减少核数**（把三个小核融进相邻 GEMV 的 epilogue），而不是优化它们的算术。

⚠️ 注意 `LINGXI_GR_FUSE`（5 核→2 核）实测 **+7.5% 更差**（§7）——但那一路**不在图捕获区内**
（它在捕获逻辑之前 return），所以"融合更差"里很可能混着"丢了图重放"的代价。
⇒ 若要做融合，**必须让它保持可捕获**，否则会重复 GR_FUSE 的假阴性。

## 3.54 杠杆 #1 被自己的实测否掉：`[moe] router` 段不是"router 的工作量"

上表里"MoE router 搬设备 ~2.9 ms（12%）"是**基于 `[moe] router` 段**推的。本轮用
**不带 KTS 的 `LINGXI_PROF`**（纯墙钟）复核，20 token、959 层的平均：

```
shared=16.6  router=601.4  专家=55.4  合计=673.4  µs/层
```

`router` 段 601 µs/层 —— **这不可能是"host 做 softmax+top-10"的代价**（那部分只 512 次 `expf`
+ 5120 次比较 ≈ 15 µs）。真相是：**这一段结束于一次 `k.stream.synchronize()`**，
所以它**吸收的是它之前所有已入队工作的排空**（shared 专家 + router GEMV + 在途 DMA 的尾巴）。
⇒ **与 KTS 那个仪器伪影同源**（§3.42 已记"每插一次同步就排空一次流水"）；
即使是纯墙钟口径，**只要区段以 sync 结尾就会被污染**。

**⇒ 修正结论**：
- **"MoE router 的 host 往返 = 2.9 ms" 证据不成立**，从杠杆表里划掉（预期收益应从 12% 降级为
  "至多 ~0.7 ms / 3%：只省 `expf`+选择的 CPU，因为设备端算完 top-k 后 host 仍要拿一次路由
  去做专家槽管理，sync 省不掉"）；
- **真正的结构性成本是"每层一次 sync"**：它由 **host 侧专家槽缓存**强制（路由是槽管理的数据依赖），
  48 次/token 把流水压得很浅。要根除只能把**槽管理也搬设备** —— 这正是文档早已标注的
  "设备端 top-k / 槽管理**会破坏位级复现、需用户拍板**"那一项。

## 3.55 杠杆 #2 也不成立：GR 的三个"小核"**没有可融的交集**

§3.53 我写了"可融的是 `mix_mean`+`inject`（同读 xn）"——**这条是错的**，本轮细看后修正：

| 算子 | 形态 | 能否融 |
|---|---|---|
| `norm` | **生产者**（它的输出 `xn` 是后两个 GEMV 与 `mix_mean` 的输入） | ✗ 必须先算完 |
| `inject` | **[4, 10240] 的 GEMV** —— 每个输出要对全长 10240 做**完整归约** | ✗ |
| `mix_mean` | **逐元素**（对 hc 求均值，`grid=H/128 × rows`） | ✗ |

`inject` 要"整行归约"、`mix_mean` 是"逐元素"，塞进同一个 kernel 就得让一个 block 同时干
41K MAC 与 2560 个输出 —— rows=1 时就是 **1 个 block**，严重欠并行。**三条都不成立** ⇒
§4 表里的杠杆 #2（~7%）**降级为"无可落地的实现"**，与 `LINGXI_GR_FUSE`（5→2 核、实测更差）一致。

**⇒ 由此得到一个重要结论：块级已经**接近局部最优**。** 剩下真正能动的只有两条：

1. **1b 设备端槽管理**（~12%）：§3.54 已把成本正确归因 —— 不是"host top-k 慢"，而是
   **每层一次 sync 造成的流水排空**（`router` 段 601 µs/层 量到的就是它）。根除它必须把
   专家槽表也搬设备（设备端 LRU + 槽命中直接读显存、miss 才过 PCIe 读锁页 host arena）。
   代价：**破坏位级复现** —— 用户此前已表示"位级不可复现的话到时候看实际输出"。
2. **4 投机解码**（1.5~2.5×）：MTP 权重现成同源，卡在草稿接受率仍 0（§3.52）。

## 3.59 **MTP 的 MoE 走的是"逐专家 bf16 累加"路，与主干不是同一条数值路**

§3.58 的嫌疑本轮被代码坐实，而且找到了**具体的数值差异**：

```rust
// moe.rs:402 —— src=None（= MTP）时 fast_path 恒 false
let fast_path = pair_path || (src.is_some() && rows == 1 && !hit_ids.is_empty());
```

| | 主干（生产） | **MTP 草稿层** |
|---|---|---|
| `fast_path` | true（`src=Some`） | **false（`src=None`）** |
| 专家段归并 | `moe_combine_rows_bf16`：**按行整体加权、f32 累加、只舍入一次** | **`expert_out` 是 bf16 且零初始化 → 逐专家 `scatter_add_rows_bf16` 累加** |
| 舍入次数 | **1** | **每个专家 1 次（10 个专家 = 10 次舍入回 bf16）** |

⇒ **同一个 MoE，两条路算出来的数值不同**（慢路径多 9 次 bf16 舍入，约 1e-2 量级扰动）。
这与"**只有 MTP 错、主干全对**"完全自洽：MTP 单层承受这 1e-2 扰动 → 它的输出 hidden 被推偏 →
`argmax` 系统性错开 ⇒ 接受率 ≈ 0（而非"偶尔错"）。

**修复方向（两条，都不大）**：
1. **给 MTP 一个"常驻权重版 `ExpertSource`"**，让它的 MoE 走 `src=Some` 的快路径（`rows==1` 那条）
   —— 与主干同一条数值路，**不碰主干**。需要：一个 `ResidentSource`（在设备上按 `hit_ids` gather
   出 10 个专家的行到紧凑 scratch，2 × ~1.5 MB/层）+ 把 MTP 的 `layer_step` 接上它。
2. 或把慢路径改成 **f32 暂存、最后一次舍入** —— 需要一个 f32 的 scatter-add 核（**当前不存在**：
   `lib.rs` 里只有 `scatter_add_rows_bf16` 与 `moe_combine_rows_bf16`），再加一次 f32→bf16 收尾。

**⚠️ 关键事实（本轮确证，让修复更安全）**：**慢路径在生产上不可达** ——
`fast_path == false` 只发生在 `src=None`（= MTP）或 `LINGXI_NO_PAIR_MOE=1`（A/B 调试开关）时；
主干 prefill 是 `rows>1 + src=Some + q4_hits` ⇒ 走 `pair_path` 快路径。
⇒ **改慢路径不会动到主干任何生产数值**，方案 2 的风险比我原先估的低得多。

**验证方法**：接上常驻 source（或改完慢路径）后重跑 `mtp-accept`，接受率应从 0 跳起来。

## 3.60 **§3.59 的假设被否掉** —— 并因此得到一个更重要的推论

零代码实验：`LINGXI_NO_PAIR_MOE=1` 会**强制主干 prefill（rows>1 + src=Some）也走那条慢路径**，

## 3.63 从"输出特征"抓到的新线索：草稿的 token 分布与主干**系统性不同**

一次零改动的 `mtp-accept`（prompt 2 token，n_new 64）逐步输出：

```
step  1  主干=22      draft=22760
step 17  主干=19      draft=191614
step 33  主干=220     draft=76664
step 49  主干=271     draft=35116
step 64  主干=19      draft=135658
```

两个特征：
1. **草稿在各步变化**（22760/191614/76664/35116/135658）⇒ 不是常数、不是读到垃圾内存，
   **它确实在算东西**；
2. **草稿一律是几十万级的大 id，而主干一律是 22/19/220/271 这类小 id** ⇒ **两个分布系统性不同**。
   词表 3200 万（PLE 表 `[160, 32001536]`），大 id 合法；但在主干偏好小 id 的上下文里，
   草稿一律挑超大 id ⇒ **草稿的 logits 实质是乱序的**。

**⇒ 最直接的机制：喂给输出头的那份 hidden 尺度不对。** 与 §前文 `LINGXI_MTP_STATS` 的量测对得上：

| | std |
|---|---|
| 主干残差栈（MTP 的 h 输入） | **0.5 ~ 0.7** |
| MTP 尾部 `mixer` 输出（= 喂头的 hidden） | **3.2** |

**差 4~6 倍。** ⇒ 下一步验证很便宜：**把主干自己那份 `mixed`（喂头的 hidden）的 std 也量出来**
——若主干的 `mixed` 量级是 0.5~1 而 MTP 的是 3.2，则**MTP 的尾部 mixer 吃错了输入**（或该处少了一次
归一化），这一条就足以解释"logits 乱序 ⇒ 0/64"。

**⇒ 这也是迄今最"范畴性"的一条线索**（分布层面必然错），优先于继续试喂法变体。

## 3.64 **最可疑的根因**：最后一步该用"全局 mixer"，我用的是 `mtp/mixer`

查主干产物（零改动）确认了结构：

```

  text/hyper_connection_mixer/{hc_norm, mix_down, mix_up}
      ↑ 末层残差栈 → 这里 → text/output_head
MTP：另有一套自己的
  mtp/mixer/{hc_norm, mix_down, mix_up}
```

**而 Strata（已验证能跑 `--mtp mtp/rt --spec 4` 的实现）在最后一步读的是全局那套**
（`mtp.cpp` L923–925：`hyper_connection_mixer.hc_norm` / `input_mix_weight_down` / `input_mix_weight_up`），
**不是 MTP 自己的 mixer**。

### 8.2 ⭐ MTP `0/n` 的真正根因：**stem norm 漏了 wplus 的 `+1`**（已修，接受率 0 → **0.906**）

**结论**：`$LINGXI_ASSETS/qwen4_exp.mtp.ninfer` 的 `mtp/embedding_norm` 与 `mtp/hidden_norm`
**漏了 wplus 的 `+1`**。本模型族 safetensors 把 **RMSNorm gamma 存成 `γ−1`**，ninfer 转换的
**`wplus`** 负责 +1 还原；转换器的 +1 名单**漏了 role = `MtpStemNorm`** 的这两个（层内的
`AttentionNorm`/`HyperConnectionNorm` 都对）。于是 stem 拿 `γ−1` 当 γ：**符号翻 + 量级差 ~3 倍**。

**判据（一眼可辨）**：gamma 必须全为正。

| 张量 | 修复前 | 补 +1 后 |
| --- | --- | --- |
| `mtp/embedding_norm` | mean **−0.7642** / 负 100.0% | **+0.2358** / 负 0.0% |
| `mtp/hidden_norm` | mean **−0.3284** / 负 84.3% | **+0.6703** / 负 0.3% |

**效果（两个 bug 逐个修）**：`mtp-accept` **0/64 = 0.000** → 修 ① 后 **0.906** → 再修 ② 后
**64/64 = 1.000**；多 prompt：`The capital of France is` 96/96、`1..10` 96/96、
`def fibonacci(n):` 86/96 = 0.896、`Write a short poem…` 78/96 = 0.812 ⇒ **实际 0.81~1.00**。
prompt 段真值强核对 0/21 → 8/21，偏移扫描**只在 k=+0** 命中 ⇒ 语义正确。

**② `query_key_gate_value` 的行序也错了**：它的行序**不是** `[q_proj;k_proj;v_proj]` 的真置换
—— 在 q 段里插了一个 k 块 ⇒ **丢 256 行 q、重复 256 行 k**。
正确行序 = `q(6144)|k(512)|gate(6144)|v(512)`（q/gate 按头去交织：`h*256+d ← q_proj[h*512+d]`
与 `q_proj[h*512+256+d]`），**用主干产物（golden 金标准）layer 3 逐行验证过**。
⚠️ 判据是**"行多重集 == `[q;k;v]`"**：逐行哈希反查**抓不到**它（重复行照样每行命中）。

**③（工具侧）`+1` 必须 round-half-even，不能截断**：我的转换器最初写成 `>>16`（截断），
于是每个 `+1` 后的 gamma 与主干差 ~25% 元素（各差 1 ulp、且总是偏低）。
改为 round-half-even 后与主干产物**逐位 100% 一致**（已用主干 3 个 norm 验证，2560~10240 元素全同）。

**产物与工具**：用仓库转换器从原始 safetensors 生成（**不要**用 `mtp-pack` 那份）：
`python3 tools/convert/hf2lingxi.py mtp --src $MODELS/nvfp4/Qwen3.8-Flash-Next \
--out $LINGXI_ASSETS/qwen4_exp.mtp.fixed.ninfer --strict`
自带两道自检（gamma 全为正 / qkv 真置换），正好各抓一个 bug；
产物与原产物 **25/27 张量逐位同，差异恰好只有那 3 处 bug**。

**用这条推翻的旧假设（别再试）**：~~"MTP 与主干不同源/借了 BASE 的 MTP"~~ —— 实测主干产物
`qwen4_exp.ninfer` 逐位等于 `RVN-Qwen3.8-Flash-Next-Abliterated-Uncensored`，MTP 26/27 张量逐位等于
`Qwen3.8-Flash-Next` 的 `mtp.*`，两者专家权重 rel≈5.5e-2 **不是** 0/n 的原因。
也否掉 ~~"最后一步该用全局 mixer"~~（§3.64）与 ~~"MoE 慢路径累计精度"~~（§3.60）。

**方法论教训（本轮最重要）**：§3.56/§3.57 的"白盒通过"是**循环论证** ——
它们拿**同一份产物的权重**去比 Rust，权重本身错了永远查不出来；而主干侧没有 stem norm，
所以主干判据也照不到。**凡"比实现"的对拍，先问参照物是否独立**（本次靠"HF 原始权重当独立参照"
+ "gamma 必须全为正"的先验才破局）。

**零/低算力判据（本轮新增，值得复用）**：
- `LINGXI_NO_GRAPHS=1` 草稿逐位不变 ⇒ 排除 CUDAGraph 键冲突；
- `mtp-accept` 的 **`[h 对齐]`**：主干自己的 h 过 mixer+head 的 argmax == `ids[i+1]`（实测 16/23）
  ⇒ 喂 MTP 的 h 位置对齐；**`[偏移扫描]`**：草稿对 ids 的 ±2 偏移命中 ⇒ 区分"错位"与"算错"；
- 把某个张量**清零/替换**再看输出是否变化 ⇒ 判定该张量**是否真的进了计算路径**
  （本轮靠它发现"改 94% 的 o_proj 草稿却逐位不变"，从而知道 logits 已饱和成离群值）。

### 8.3 下一步：投机环路（拿到吞吐还没做）

接受率 0.81~1.00 只是**接受率**。吞吐要靠引擎里的**投机环路**：
`草稿 k 个 → 一次主干前向验证 → 接受前缀 → 提交`。**lingxi 目前没有这条环路**
（`mtp-accept` 只测接受率）⇒ 这是通往 200 tok/s 的下一块主要工作。

### 8.4 ⚠️ 但先把"200 到底可不可能"算清楚（`LINGXI_FWD_BENCH` 实测，2026-10-16）

`LINGXI_FWD_BENCH="1,2,4,6,8,12"`（48 层建好后、空状态、热 provider）：

| t | 一次前向 median | 每 token-slot |
| --- | --- | --- |
| 1 | **29.0 ms** | 29.0 |
| 2 | 37.1 ms | 18.6 |
| 4 | 51.7 ms | 12.9 |
| 6 | 65.7 ms | 11.0 |
| 8 | 78.6 ms | 9.8 |
| 12 | 114.9 ms | 9.6 |

**线性拟合（t=1..8）**：`cost(t) ≈ 21.9 ms + 7.1 ms × t`。
- **截距 21.9 ms** = 每趟把稠密权重读一遍（19.4 GB ≈ 0.9 TB/s 峰值下的 ~26 ms 量级；实测 21.9）。
  ⇒ **投机正是要把这 21.9 ms 摊销到 (1−p^{k+1})/(1−p) 个 token 上**。
- **边际 7.1 ms/token** —— 这一段是**专家段**：每 token 每层 10 个专家 × 2.6 MB，
  一趟 t=k 要 48×10k×2.6 MB。反推有效带宽 ≈ **174 GB/s**（与 §3.16/§3.52 的专家 GEMV
  170~377 GB/s 完全一致）⇒ **边际成本的大头是专家 GEMV 的效率，不是字节数**。

**投机天花板（代公式）**：一轮 = `cost(k+1)`，产出 = `(1−p^{k+1})/(1−p)` 个 token。

| p（接受率） | k | 一轮耗时 | token/轮 | ms/token | tok/s |
| --- | --- | --- | --- | --- | --- |
| 0.90 | 4 | 57.4 ms | 4.10 | 14.0 | **71** |
| 0.90 | 6 | 71.6 ms | 5.22 | 13.7 | **73** |
| 1.00（完美草稿） | 7 | 78.6 ms | 8.00 | 9.8 | **102** |

⇒ **结论：即便草稿头 100% 接受，本引擎+本硬件的天花板也只有 ~100 tok/s**；
= 0.9 时约 **73 tok/s**。**200 tok/s 现在不可达**，缺的是**把边际那 7.1 ms 打下去**。

**两条把边际打下去的路（都可验证）**：

1. **专家 GEMV 效率 174 → 500~700 GB/s**：边际 7.1 → ~1.8 ms/token。
   代入 p=0.9/k=6：一轮 = 21.9+1.8×6 = 32.7 ms / 5.22 = **6.3 ms/token ≈ 160 tok/s**
   —— 这是**当前看到的最接近 200 的路**。§3.16/§3.32 已记：瓶颈不是带宽而是
   nibble→float 的发射率（LUT 已做过一轮，+20~26%）；再往下需要新设计（文档 §4 的 #2b）。
2. **降专家字节数**：专家已是 Q4（2.6 MB/专家）。若降到 3 bit ⇒ 字节 −25%，
   边际按比例降 ⇒ 约 +33% 吞吐。但用户已定"优先 W4A16，不用 IQ3 系" ⇒ 需拍板。

**另一条硬上限（提醒）**：每 token 必须过的字节 = 1.25 GB（专家）+ 19.4/(k+1) GB（稠密摊销）。
k=6/p=0.9 时 ≈ 26.9 GB/轮 ÷ 5.22 = 5.2 GB/token；200 tok/s 意味着 **1 TB/s** 的持续流——
**超过 V100 的 HBM 峰值**。所以 200 在本模型上**不只受算力限制，是带宽墙**；
要过墙只能"少读字节"（更狠的量化 / 更稀疏 / 更小的模型）。

**⇒ 下一步（按性价比排序）**：
1. **实现投机环路**（37 → ~73 tok/s，1.9×）—— 需要**状态回卷**：
   QSA 只要回卷 `len`（便宜）；**GDN 是循环状态**，需在每轮开始快照 `s_all`+`k_hist`
   （36 层 ≈ 115 MB，D2D ~0.2 ms），部分接受后**只重放被接受前缀的 GDN**（保存每层输入
   1.3 MB 即可，重放成本 ≈ 5 ms/轮）。
2. **啃专家 GEMV 的发射率**（边际 7.1 → 1.8）—— 这是唯一能把天花板推到 ~160 的方向。

### 8.5.4 【重大】`LINGXI_FWD_BENCH` 是**瞎的**：它测不到专家 H2D

`LINGXI_FWD_BENCH` 构造的 id 是 `prompt_ids[i % prompt_ids.len()]` —— **重复的 prompt token**！
于是每个 t 都路由到**同一小撮专家**，槽缓存永远 100% 命中 ⇒ **这条尺子天生看不到专家 DMA**。

用它得出的「专家 H2D 只值 3.4 ms @t=8」**是错的**。换到真负载（`mtp-accept` 的投机环路，
token 是新的）立刻现原形：

| l 口径（kd=6，t=7 主干验证） | 每轮 ms |
| --- | --- |
| 真负载（`LINGXI_MTP_SPEC=6`） | **177~180** |
| `LINGXI_ARENA_NOH2D=1`（只记槽、不真拷 DMA） | **78.4** |

⇒ **专家 blob 的 H2D（PCIe）占 t>1 主干前向的 ~56%（约 99 ms/轮）**。这才是 t>1 的真正第一大项，
**不是** GEMV 带宽、**不是** attention。

**量级自洽**：PCIe 上 99 ms × ~12 GB/s（GPU0 x16 gen3）≈ **1.2 GB/轮** ÷ 2.61 MB/专家 ≈ **460 次 miss**；
一轮唯一专家 ≈ 7×10×48 ≈ 3168 ⇒ **miss 率 ~14.5%**，7000 槽（≈2.2 轮历史）装不住这个工作集。

⚠️ **NOH2D 的数只能当"上界/方向"**：它不真拷 ⇒ 槽里是旧专家 ⇒ 数学作废 ⇒ 路由改变 ⇒ 后续轮的
miss 结构也跟着变（那一次跑出来的是退化的重复序列、接受率 4.75/6）。**要精确数 miss 得直接打命中率统计。**

`[13312,2560]` 510→503、`[ 320,10240]` 123→110、`[10240, 320]` 234→216、`[2560,640]` 165→160。

### 8.5.7 到 200 tok/s 的真实账（**不是带宽墙，也不是 GEMV 效率墙 —— 是 PCIe 墙**）

**真负载下一轮（kd=6, t=7）的 218 ms 拆开：**

| 项 | ms/轮 | 占比 | 性质 |
| --- | --- | --- | --- |
| **主干专家 blob 的 H2D（PCIe x16）** | **~99** | **45%** | 460 次 miss × 2.61 MB @ ~12 GB/s |
| 主干其余（attention + GR + 专家 GEMV + 稠密） | ~78 | 36% | 与 FWD_BENCH 同量级 |
| MTP 重放（36 层 GDN 重放 + PLE/GR） | 18.8 | 9% | |
| 草稿链（6 次 MTP 层前向 + 每步 1.27 GB lm_head） | 15.4 | 7% | |
| 提交（快照恢复 + QSA 回卷） | 3.4 | 2% | |

**字节账**（t=7，真实路由，Q4 已按 0.5 B/参数计）：专家 ~8.3 GB（**其中 ~1.2 GB 每轮要走 PCIe**）
+ 稠密 ~2.9 GB + GDN 状态 ~1.6 GB ≈ **12.8 GB/轮**。
- HBM 地板 = 12.8/900 = **14.2 ms/轮** ⇒ 完美草稿 8/14.2 = **563 tok/s**。
- 现在 218 ms ⇒ 有效 59 GB/s，**HBM 利用率 6.5%**。

**⇒ 优先级（按"每 ms 收益"排）：**

1. **把专家 H2D 干掉/藏掉**（值 ~99 ms/轮 = 45%）。三条可选路径，按可行性排：
   a. **分块流水**：把每层的 miss 切成小批（比如每次 8 个专家），copy stream 与 compute stream 交替
      —— 只能藏掉 GEMV（~27 ms/轮），**收益上限有限**（DMA 本身 99 ms > 计算 27 ms）。
   b. **降 miss 率**：容量已到顶（8.5.4c）；**换淘汰策略**是唯一剩下的空间 ——
      现在是全局 LRU，对"48 层每层各 ~66 个专家"的循环式访问，全局 LRU 会让某层的热专家
      被另一层的冷专家挤掉。试**按层配额**（7000/48 ≈ 145 槽/层，层内 LRU，且保护本轮的专家）。
      **这是最便宜、最可能有效的一步。**
   c. **少读字节**：专家已是 Q4；再降就是 3 bit（用户已定不用 IQ3 系）。
2. **草稿链接受率 0.76 → 0.9+**（把 2.57/6 提到 ~4.5/6 ⇒ 同一轮成本下产出 +75%）。
   单步 0.958 说明 MTP 头本身没问题，**问题在自喂链的 KV/状态接线**。
3. **把 `talk` 接上投机环路** —— 否则 `bench.sh` 这条权威尺子永远量不到 ≥100 tok/s 的任何进展。
4. **非专家的 t 边际 4.01 ms/token**（`lingxi_gdn_recurrent_bf16` 只有 48 个 block / 179 GB/s；
   `attn_masked` 只有 24 个 block）—— 等 1/2 做完再回来收。

### 8.6.4 硬算术：单流 200 tok/s 差在哪

**单流（顺序）每 token 的 26.8 ms 拆开**：

| 项 | ms | 占比 | 能不能消 |
| --- | --- | --- | --- |
| 专家 H2D（PCIe） | **7.0** | 26% | **只能重叠，不能消**（路由要等本层前半段跑完，DMA 天然在关键路径上） |
| 真核（按 launch-bench 速率算） | ~11.6 | 43% | 能，但要**提高核效率**（现在普遍 300~500 GB/s，峰值 900） |
| host（topk 1.0 + MoE 前置/上传 ~2.4） | ~3.4 | 13% | 能（改 host 代码） |
| 同步/排空 + 各式小核零头 | ~4.8 | 18% | 部分能 |

- **HBM 地板**：每 token 4.6 GB（专家 1.25 + 稠密 3.35）⇒ **5.1 ms = 196 tok/s（100% 峰值）**。
  ⇒ **顺序路径在物理上就到不了 200**（要到 200 得 5.0 ms/token = 92% 峰值，且 DMA 必须完全重叠）。
- **零开销（理想核效率）**：11.6 ms ⇒ **86 tok/s**。

**投机路径（kd=6，t=7）**：一轮 218 ms 产出 3.57 token = **17.0 tok/s**（顺序 19 ⇒ 仍是净亏）。

| 项 | ms/轮 | 占比 |
| --- | --- | --- |
| 专家 H2D | ~99 | 45% |
| 主干其余 | ~78 | 36% |
| MTP 重放 | 18.8 | 9% |
| 草稿链 | 15.4 | 7% |
| 提交 | 3.4 | 2% |

- 完美草稿 + 零开销：`(1.6 稠密 + 8.3 专家) GB / 900 GB/s ≈ 11 ms/轮` ⇒ 8/11 = **727 tok/s**。
- 现接受率（p_eff ≈ 0.76）下每轮 3.57 token ⇒ 要 200 tok/s 得 **17.8 ms/轮**
  ⇒ 比现在快 **12×**。

**⇒ 结论（必须记住）：**
**200 tok/s 不是"再优化几个核"能到的**。当前的有效带宽只有 **~170 GB/s = 峰值的 19%**，
而瓶颈是**结构性的三条**：
1. **26% 的 token 时间在 PCIe 上**（专家离身），且**无法被计算重叠**（路由时序决定的）；
2. **专家常驻率被 32 GB 显存锁死**：全专家 64 GB / Q4，槽最多 7000（17 GiB，7500 就 OOM）；
3. 核效率只有峰值的 30~55%（Q4 专家核 375/245 GB/s、稠密 Q4 366~523、GR 253）。

**唯一有 >1.5× 潜力的结构改动**：**用 GPU1 的 32 GB 空显存做专家常驻**（专家并行）。
- 2×32 GB = 64 GB **恰好装得下全部 24576 个专家的 Q4（60 GB）** ⇒ **H2D 归零**；
- 层内跨卡流量只有「`t×2560` 输入 + `10t×2560` 输出 ≈ 56 KB/token」（GPU1 是 x8，约 10 µs），
  远小于 GPU0 现在的 89 MB/token；
- 代价：GPU1 的 x8 链路 + 历史上有跨卡 CmpltTO 掉卡记录（§project_memory）；
  **必须先做一次"低流量跨卡 48 层"的稳定性验证**再谈收益。

**⇒ 在拍板 (GPU1 专家常驻) 之前，先做的三件事（都在单卡内、都能验证）：**
1. **host 侧 MoE 提速**（值 ~3.4 ms/token = 13%）：把 512 次 `exp` 的 softmax 移到设备端
   （**必须逐位一致地复现**），把每层十几个 Vec/上传改成复用缓冲。
2. **专家 H2D 与"常驻专家的 GEMV"重叠**（值 ≤ min(7, 3.3) ms = 12%）：hit/miss 分组 + 第二条 stream。
3. **草稿链接受率**（值 +75% 产出，不改单轮成本）：单步 0.958 vs 链路 2.57/6 ⇒ 查自喂链接线。

## 8.7 2026-10-16（第四轮）：**"用 GPU1 那 32 GB 做专家常驻"这条路 —— 实测判死**

探针：`tools/gpu/gpu_peer_probe.cu`（**只读、不碰 arena/不写 /dev/shm**）。
编译 `nvcc -O2 -arch=sm_70`，运行 `/tmp/gpu_peer_probe <token数> <host→GPU1 GiB>`。

### 8.7.1 ①③ P2P 被 **IOMMU（VT-d / DMAR）** 挡死：**API 说可用，实测 0.0001 GB/s**

```
cudaDeviceCanAccessPeer(0→1) = 1     EnablePeerAccess(0→1) = 1     ← CUDA 说"可用"
peer 5 KB   (激活)            49276.9 µs/次  →   0.0001 GB/s      ← 实测是灾难
peer 2.61 MB (单专家 blob)    78149.9 µs/次  →   0.0003 GB/s
peer 2.61 MB (GPU1→GPU0)      86700.0 µs/次  →   0.0003 GB/s
本机 HBM 2.61 MB (对照)          34.1 µs/次  →  76.63 GB/s
```

宿主 `dmesg` 同步出现**每次 DMA 一条**的 IOMMU 故障，设备就是 **44:00.0 = GPU1**：

```
DMAR: [DMA Write NO_PASID] Request device [44:00.0] fault addr 0x3b800003000
      [fault reason 0x05] PTE Write access is not set
```

⇒ **这是"故障 + 回退"路径**：每次 peer 拷贝都先撞 IOMMU、再退回慢路。
**⚠️ 教训：判 P2P 能不能用，绝不能只看 `cudaDeviceCanAccessPeer` / `EnablePeerAccess` 的返回值，
必须实测带宽**（本次两个 API 都是 1，带宽却是 0.0001 GB/s，差 6 个数量级）。

**好消息**：两块卡**都没有掉**——跑完 `nvidia-smi` 仍是 `0,1 MiB / 1,1 MiB`、无新 Xid。
DMAR 故障停在探针被杀那一刻（240 → 445 条，全是它刷的）。

> 如果哪天想救 P2P：Linux 侧标准修法是宿主开 **`iommu=pt`**（passthrough，IOMMU 不做翻译）。
> **但那要重启宿主**（会丢 `/dev/shm` 里的 60 GB arena —— 好在
> `$LINGXI_ASSETS/qwen4_exp.expert-arena.q4g64.bin` 有同尺寸的持久副本，
> 或按 `$DATA/tmp/quantize_expert_arena.py` 重生成；回灌走 sdb 要按磁盘铁律 ≤15 min/块）。
> **是否重启由用户拍板，本轮不动。**

### 8.7.2 ②' 退到 host 中转 —— **延迟就吃掉大半收益**

P2P 死了之后唯一的路是 `GPU0 → 锁页 host → GPU1`（两次 PCIe 跳，走的是**已被验证安全**的普通 DMA 路）：

| | 同步往返延迟 |
| --- | --- |
| 去 5 KB（激活） | **34.0 µs/层** |
| 回 51 KB（专家输出） | **42.8 µs/层** |
| ⇒ 48 层/token | **3.69 ms/token** |

对照它要替掉的东西：单流专家 H2D = **7 ms/token**。
⇒ **净赚 ≈ 3.3 ms/token（12%）**，而代价是：① 整个 MoE 块要改成"发/收 + 每层两次同步"，
② GPU1 的专家 GEMV 也落进关键路径，③ 24 GB 灌进 GPU1 还要一次长传输。
**⇒ 判死：不值。**

### 8.7.3 更根本的：**就算 P2P 是好的，这条路也到不了 200**

上一轮我写的 "2×32 GB = 64 GB 恰好装得下全部专家 Q4（60 GB） ⇒ H2D 归零" ——
**这句算术是错的**，它漏掉了稠密权重 + KV + scratch：

| 项 | GiB | 说明 |
| --- | --- | --- |
| 全部专家 Q4 | 60.0 | 24576 × 2.61 MB |
| 稠密（Q4 后：qsa 0.30 + gdn 1.05 + head 0.32 + GR 1.19 + emb 1.18 + shared 0.44 + router 0.12 + 其它） | **≈4.7** | 必须常驻 |
| KV 池 + scratch | 2~4 | 可调但省不掉 |
| **合计** | **≈67~69 GiB** | **> 两块卡总共 63.4 GiB（31.7×2）** |

⇒ 即便 P2P 完美，也**装不下全量**，最多把槽从 7000 提到 ~21000（≈86% 常驻）
⇒ miss 7% → ~1~2% ⇒ **省 ~5~6 ms/token（≈22%）**：单流 26.8 → ~21 ms（**48 tok/s**）、
投机轮 218 → ~135 ms（**≈26 tok/s**）。
**⇒ 离 200 还差 4~5 倍，剩下的差距在核效率（300~500 GB/s vs 900）与 host 开销上，
不在"专家放在哪块卡"上。**

### 8.7.4 ⇒ 结论与接下来的路线（**回到单卡**）

1. **双卡专家常驻：判死**（P2P 被 IOMMU 挡；host 中转的 3.69 ms/token 延迟吃掉大半收益；
   且全量装不下）。这条**从"最有希望"降级为"否决登记"**。
2. **回到 §8.6.4 的三件单卡实事**（都是可验证、低风险）：
   - host 侧 MoE 提速（512 次 `exp` 的 softmax 移设备 + 复用缓冲）—— 值 ~3.4 ms/token（13%）；
   - 专家 H2D 与"常驻专家 GEMV"重叠（hit/miss 分组 + 第二 stream）—— 值 ≤3.3 ms/token（12%）；
   - 草稿链接受率 0.76 → 0.9+（不改单轮成本，产出 +75%）。
3. **对 200 tok/s 的诚实定位**：单流 200 tok/s 在**本机 + 本模型 + 单卡**上不可达
   （HBM 地板 196 tok/s 就要求 100% 峰值，而当前有效带宽 19%）。
   可期的**近期**目标是：**单流顺序 ~45~50 tok/s、投机 ~26~35 tok/s**；
   要再往上必须换赛道（例如"多流聚合吞吐"或"更小/更稀疏的模型"），不是靠继续抠内核。
